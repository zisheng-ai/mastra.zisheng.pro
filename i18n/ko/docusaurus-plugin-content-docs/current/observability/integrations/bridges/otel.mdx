# OpenTelemetry 브리지

:::경고

OpenTelemetry Bridge는 현재**experimental**. APIs and configuration options may change in future releases.

:::

OpenTelemetry(OTEL) 브리지는 Mastra의 추적 시스템과 기존 OpenTelemetry 인프라 간의 양방향 통합을 가능하게 합니다. 추적 데이터를 외부 플랫폼으로 보내는 내보내기와 달리 브리지는 분산 추적 컨텍스트에 참여하는 기본 OTEL 범위를 만듭니다.

:::info 기존 OTEL 인프라 없이 추적을 보내려고 하시나요?

기존 OpenTelemetry 계측이 없는 경우[OpenTelemetry Exporter](/docs/observability/integrations/exporters/otel) may be simpler, it sends traces directly without requiring an OTEL SDK setup.

:::

## 브릿지를 사용하는 경우 {/* #when-to-use-the-bridge */}

다음과 같은 경우 OtelBridge를 사용하십시오.

* 애플리케이션(HTTP 서버, 데이터베이스 클라이언트 등)에 기존 OTEL 계측이 있어야 합니다.
* Mastra 작업이 기존 OTEL 추적의 하위 범위로 표시되도록 하려는 경우
* 적절한 부모-자식 관계를 유지하려면 Mastra Tool 내에 OTEL 계측 코드가 필요합니다.
* 추적 컨텍스트가 서비스 전체에 전파되어야 하는 분산 시스템을 구축하고 있습니다.

## 작동 원리 {/* #how-it-works */}

OtelBridge는 양방향 통합을 제공합니다.

**OTEL에서 마스트라까지:**

* OTEL 주변 컨텍스트(AsyncLocalStorage)에서 자동으로 읽습니다.
* 활성 OTEL 범위에서 추적 ID 및 상위 범위 ID를 상속합니다.
* OTEL 샘플링 결정을 존중합니다. 추적이 샘플링되지 않으면 Mastra는 이에 대한 범위를 생성하지 않습니다.
* OTEL 자동 계측이 활성화된 경우 수동 추적 ID 전달이 필요하지 않습니다.

**마스트라에서 OTEL까지:**

* Mastra 작업(Agent, LLM 통화, Tool, Workflow)을 위한 기본 OTEL 범위를 생성합니다.
* 분산 추적에서 적절한 상위-하위 관계를 유지합니다.
* Mastra 작업 내에서 OTEL 계측 코드(HTTP 클라이언트, 데이터베이스 호출)가 올바르게 중첩되도록 허용합니다.
* Mastra 로그 이벤트를 전 세계적으로 등록된 OTEL로 전달합니다.`LoggerProvider`. Logs that originate inside a Mastra span are emitted under that span's OTEL context so backends correlate them with the trace. If no `LoggerProvider` is registered, log emission is a silent no-op.

## 설치 {/* #installation */}

```bash npm2yarn
npm install @mastra/otel-bridge
```

브리지는 기존 OpenTelemetry 설정과 함께 작동합니다. 구성에 따라 다음 패키지 중 일부가 필요할 수도 있습니다.

* `@opentelemetry/sdk-node`- OTEL용 핵심 Node.js SDK
* `@opentelemetry/auto-instrumentations-node`- 공용 라이브러리에 대한 자동 계측
* `@opentelemetry/exporter-trace-otlp-proto`- OTLP 내보내기(HTTP를 통한 Protobuf)
* `@opentelemetry/exporter-trace-otlp-http`- OTLP 내보내기(HTTP를 통한 JSON)
* `@opentelemetry/exporter-trace-otlp-grpc`- OTLP 내보내기(gRPC)
* `@opentelemetry/sdk-trace-base`- 기본 추적 SDK(BatchSpanProcessor 등용)
* `@opentelemetry/core`- 핵심 유틸리티(W3CTraceContextPropagator 등용)
* `@opentelemetry/sdk-logs`OTLP 로그 내보내기(예:`@opentelemetry/exporter-logs-otlp-http`) - Required if you want the bridge to forward Mastra log events too

## 구성 {/* #configuration */}

OtelBridge를 사용하려면 다음 두 단계가 필요합니다.

1. 애플리케이션에서 OpenTelemetry 계측 구성
2. Mastra 관측 가능성 구성에 OtelBridge를 추가하세요.

### 1단계: OpenTelemetry 계측 {/* #step-1-opentelemetry-instrumentation */}

OTEL을 초기화하는 계측 파일을 만듭니다. 이는 애플리케이션 코드보다 먼저 실행되어야 합니다.

```typescript title="instrumentation.ts"
import { NodeSDK } from '@opentelemetry/sdk-node'
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node'
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-proto'
import { BatchSpanProcessor } from '@opentelemetry/sdk-trace-base'
import { W3CTraceContextPropagator } from '@opentelemetry/core'

const sdk = new NodeSDK({
  serviceName: 'my-service',
  spanProcessors: [
    new BatchSpanProcessor(
      new OTLPTraceExporter({
        url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT || 'http://localhost:4318/v1/traces',
      }),
    ),
  ],
  instrumentations: [getNodeAutoInstrumentations()],
  textMapPropagator: new W3CTraceContextPropagator(),
})

sdk.start()

export { sdk }
```

### 2단계: 마스트라 구성 {/* #step-2-mastra-configuration */}

Mastra 관측 가능성 구성에 OtelBridge를 추가합니다.

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'
import { OtelBridge } from '@mastra/otel-bridge'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-service',
        bridge: new OtelBridge(),
      },
    },
  }),
  agents: {/* your agents */},
})
```

브리지를 사용할 때 Mastra 내보내기가 필요하지 않으며 추적은 OTEL SDK 구성을 통해 전송됩니다. 추적을 추가 대상으로 보내려는 경우 선택적으로 Mastra 내보내기를 추가할 수 있습니다.

### 로그 전달(선택사항) {/* #forwarding-logs-optional */}

또한 브릿지는 Mastra 로그 이벤트를 전 세계적으로 등록된 OTEL로 전달합니다.`LoggerProvider`. To wire up logs alongside traces, register a `logRecordProcessor` on `NodeSDK`:

```typescript title="instrumentation.ts"
import { NodeSDK } from '@opentelemetry/sdk-node'
import { OTLPLogExporter } from '@opentelemetry/exporter-logs-otlp-http'
import { BatchLogRecordProcessor } from '@opentelemetry/sdk-logs'

const sdk = new NodeSDK({
  // ...trace config as usual
  logRecordProcessor: new BatchLogRecordProcessor(
    new OTLPLogExporter({
      url: process.env.OTEL_EXPORTER_OTLP_LOGS_ENDPOINT || 'http://localhost:4318/v1/logs',
    }),
  ),
})
```

Mastra 범위 내에서 발생하는 로그는 해당 범위의 OTEL 컨텍스트에 따라 방출되므로 Datadog, Grafana 및 Honeycomb과 같은 백엔드는 이를 주변 추적과 자동으로 연관시킵니다. 추적 컨텍스트가 없는 로그는 현재 활성 OTEL 컨텍스트를 사용합니다.

등록하지 않은 경우`LoggerProvider`, log emission is a silent no-op, traces continue to work as configured.

### 애플리케이션 실행 {/* #running-your-application */}

사용`--import` flag to ensure instrumentation loads before your application:

```bash
tsx --import ./instrumentation.ts ./src/index.ts
```

## 의미론적 규칙 {/* #semantic-conventions */}

OtelBridge는 다음을 사용하여 Mastra 스팬을 내보냅니다.[OpenTelemetry Semantic Conventions for GenAI v1.38.0](https://github.com/open-telemetry/semantic-conventions/tree/v1.38.0/docs/gen-ai). This includes standardized span names (`chat {model}`, `execute_tool {tool_name}`, etc.) and attributes (`gen_ai.usage.input_tokens`, `gen_ai.request.model`, etc.).

범위 이름 지정 및 속성에 대한 자세한 내용은 다음을 참조하세요.[OpenTelemetry Exporter semantic conventions](/docs/observability/integrations/exporters/otel#opentelemetry-semantic-conventions).

## 추적 계층 구조 {/* #trace-hierarchy */}

OtelBridge를 사용하면 추적이 OTEL 및 Mastra 경계에서 적절한 계층 구조를 유지합니다.

```
HTTP POST /api/chat (from Hono middleware)
└── agent.assistant (from Mastra via OtelBridge)
    ├── chat gpt-5.4 (LLM call)
    ├── tool.execute search (tool execution)
    │   └── HTTP GET api.example.com (from OTEL auto-instrumentation)
    └── chat gpt-5.4 (follow-up LLM call)
```

## 다중 서비스 분산 추적 {/* #multi-service-distributed-tracing */}

OtelBridge는 서비스 경계를 ​​넘어 추적 전파를 가능하게 합니다. 서비스 A가 HTTP를 통해 서비스 B를 호출하면 추적 컨텍스트가 자동으로 전파됩니다.

```
Service A: HTTP POST /api/process
└── HTTP POST service-b/api/analyze (outgoing call)

Service B: HTTP POST /api/analyze (incoming call - same trace!)
└── agent.analyzer (Mastra agent inherits trace context)
    └── chat gpt-5.4
```

두 서비스 모두 다음을 갖추고 있어야 합니다.

1. OTEL 계측 구성됨
2. W3C 추적 컨텍스트 전파자가 활성화되었습니다.
3. OtelBridge가 구성된 Mastra

## 태그 사용 {/* #using-tags */}

태그는 OTEL 백엔드에서 추적을 분류하고 필터링하는 데 도움이 됩니다. Agent 또는 Workflow를 실행할 때 태그를 추가합니다.

```typescript
const result = await agent.generate('Hello', {
  tracingOptions: {
    tags: ['production', 'experiment-v2', 'user-request'],
  },
})
```

태그는 JSON 문자열로 내보내집니다.`mastra.tags` span attribute for broad backend compatibility. Common use cases include:

* 환경 라벨:`"production"`, `"staging"`
* 실험 추적:`"experiment-v1"`, `"control-group"`
* 우선순위 수준:`"priority-high"`, `"batch-job"`

## 문제 해결 {/* #troubleshooting */}

추적이 예상대로 표시되지 않거나 연결되지 않는 경우:

* OTEL SDK가 Mastra 이전에 초기화되었는지 확인합니다(사용`--import` flag or import at top of entry point)
* 관측 가능성 구성에 OtelBridge가 추가되었는지 확인하세요.
* OTEL 백엔드가 실행 중이고 액세스 가능한지 확인하세요.
