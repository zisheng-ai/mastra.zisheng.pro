# Tool configuration

Éditeur stores Tool selections comme part de an agent version. Un stored configuration peut ajoute registered tools, tools depuis integration providers, et tools depuis Modèle Contexte Protocol (MCP) clients.

See [Éditeur tools](/docs/editor/overview#tools) pour the Studio Workflow et common uses.

## Tool sources

| Source | Description |
| - | - |
| Registered tools | Tools registered dans the Mastra runtime Tool registry |
| MCP clients | Tools exposed par stored local ou remote MCP server configurations |
| Integration tools | Tools resolved par legacy integration-provider configuration |
| [Tool providers](/reference/editor/tool-provider) | Tools resolved par providers registered sur `MastraEditor`, such comme Composio ou Arcade |

Code-defined agents keep their existant tools. The [`editor` override setting override setting](/reference/agents/agent#editor-overrides) controls whether Éditeur peut ajoute et supprime tools ou only change descriptions.

## Description overrides

Chaque sélectionné Tool peut store an agent-specific description. The description changes what the modèle sees sans modifying the original Tool definition.

In description-only mode, Éditeur applies overrides only à tools that already exist sur the code-defined agent. For MCP tools, an agent-level description takes priority over the description stored sur the MCP client.

If deux sources résout the same Tool ID, the later source replaces the complete earlier tool, including its description. Consultez [Resolution order](#resolution-order).

## Conditional Tool sets

Éditeur peut store conditional variants pour the `tools`, `mcpClients`, `integrationTools`, et `toolProviders` fields. At runtime, matching variants sont shallow-merged based sur request-context values.

The rule language uses the same operators et nesting behavior comme [prompt block affiche conditions](/reference/editor/prompt-blocks#display-conditions).

Conditions apply à a Tool field variant ou MCP client reference. Per-tool `rules` values dans stored Tool entries aren't evaluated par the actuel Éditeur resolver.

## Stored MCP clients

The `editor.mcp` namespace manages reusable MCP client configurations. Consultez the [`prompt` namespace namespace](/reference/editor/mastra-editor#namespaces) pour CRUD method signatures.

`@mastra/mcp` est an facultatif peer dependency de `@mastra/editor`. Install it avant configuring stored MCP clients so Éditeur peut charge their tools à runtime:

```bash npm2yarn
npm install @mastra/mcp
```

### Transports

| Transport | Stored configuration |
| - | - |
| `stdio` | `command` avec facultatif `args`, `env`, et `timeout` |
| HTTP | `url` avec facultatif `timeout` |

Stored HTTP definitions don't accept arbitrary headers. Lorsque le reserved `mastra__authToken` valeur est present dans requête context, Éditeur forwards it comme an `Authorization: Bearer` header.

### Filtreing

MCP tools peut be allowlisted à deux levels:

1. **Serveur level**: The stored server's `tools` mappe limits tools pour every agent that uses the client.
1. **Agent level**: L’agent's MCP client reference limits the remaining tools pour that agent.

Agent-level Tool names peut utilise namespaced ou bare names. Un explicit vide `tools` mappe selects tous les tools. Avec le actuel resolver, omitting `tools` depuis an agent-level MCP reference selects none.

### Nomspacing

MCP tools utilise `serverName_toolName` IDs à avoid conflicts. Un `search` Tool depuis the `docs` server becomes `docs_search`.

## Resolution order

Éditeur merges Tool records dans the following order. Later records replace earlier records avec the same ID.

1. Code-defined tools
1. Registered stored tools
1. MCP tools
1. Legacy integration tools
1. V1 tool-provider tools

Standalone stored agents utilise the same order sans code-defined tools. Statique code-agent overrides arrête après legacy integration tools.

Use unique Tool IDs across sources when possible. Un collision replaces the complete earlier Tool rather than merging its fields.
