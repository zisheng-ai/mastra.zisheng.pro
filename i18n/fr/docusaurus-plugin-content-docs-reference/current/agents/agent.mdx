# Agent class

The `Agent` class est the foundation pour creating AI agents dans Mastra. It provides methods pour generating responses et streaming interactions. It also handles voice capabilities.

## Exemples d’utilisation

### Instructions simples sous forme de chaînes

Passing instructions comme a chaîne ou tableau de strings est the simplest way à définit up an agent. Ce est useful pour straightforward utilise cases where you need à fournit a prompt sans additional configuration.

```typescript title="src/mastra/agents/string-agent.ts"
import { Agent } from '@mastra/core/agent'

// String instructions
export const agent = new Agent({
  id: 'test-agent',
  name: 'Test Agent',
  // highlight-next-line
  instructions: 'You are a helpful assistant that provides concise answers.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

// System message object
export const agent2 = new Agent({
  id: 'test-agent-2',
  name: 'Test Agent 2',
  // highlight-start
  instructions: {
    role: 'system',
    content: 'You are an expert programmer',
  },
  // highlight-end
  model: '__GATEWAY_OPENAI_MODEL__',
})

// Array of system messages
export const agent3 = new Agent({
  id: 'test-agent-3',
  name: 'Test Agent 3',
  // highlight-start
  instructions: [
    { role: 'system', content: 'You are a helpful assistant' },
    { role: 'system', content: 'You have expertise in TypeScript' },
  ],
  // highlight-end
  model: '__GATEWAY_OPENAI_MODEL__',
})
```

### Configurations spécifiques au fournisseur

Chaque modèle provider also enables a few different options, including prompt caching et configuring reasoning. Vous pouvez définit `providerOptions` sur the instruction level à définit different caching strategy per system instruction/prompt.

```typescript title="src/mastra/agents/core-message-agent.ts"
import { Agent } from '@mastra/core/agent'

export const agent = new Agent({
  id: 'core-message-agent',
  name: 'Core Message Agent',
  instructions: {
    role: 'system',
    content: 'You are a helpful assistant specialized in technical documentation.',
    // highlight-start
    providerOptions: {
      openai: {
        reasoningEffort: 'low',
      },
    },
    // highlight-end
  },
  model: '__GATEWAY_OPENAI_MODEL__',
})
```

### Formats d’instructions mixtes

```typescript title="src/mastra/agents/multi-message-agent.ts"
import { Agent } from '@mastra/core/agent'

// This could be customizable based on the user
const preferredTone = {
  role: 'system',
  content: 'Always maintain a professional and empathetic tone.',
}

export const agent = new Agent({
  id: 'multi-message-agent',
  name: 'Multi Message Agent',
  instructions: [
    { role: 'system', content: 'You are a customer service representative.' },
    preferredTone,
    {
      role: 'system',
      content: 'Escalate complex issues to human agents when needed.',
      providerOptions: {
        anthropic: { cacheControl: { type: 'ephemeral' } },
      },
    },
  ],
  model: '__GATEWAY_ANTHROPIC_MODEL_SONNET__',
})
```

## Chaînes de modèle

For the simplest setup, transmet `model` comme a chaîne dans `provider/model` format. Separate the provider et modèle nom avec a slash. Mastra reads the matching provider credentials depuis the environment, so this format doesn't require a provider package ou import.

Popular provider strings et credentials:

- **OpenAI**: `__GATEWAY_OPENAI_MODEL__` uses `OPENAI_API_KEY`.
- **Anthropic**: `__GATEWAY_ANTHROPIC_MODEL_SONNET__` uses `ANTHROPIC_API_KEY`.
- **Google**: `__GATEWAY_GOOGLE_MODEL__` uses `GOOGLE_API_KEY` ou `GOOGLE_GENERATIVE_AI_API_KEY`.

See [models](/models) pour pris en charge modèle IDs et [environment variables](/models/environment-variables) pour the complete provider list.

## Signaux de thread

Use Agent signals à envoie real-time input et context dans a memory thread. Message APIs sont pour user-authored input. `sendSignal()` est the lower-level API pour system-generated context.

Lorsque le target thread est running, `sendMessage()` delivers the message dans the active agent loop. Lorsque le thread est idle, Mastra starts a stream avec the message comme the premier input par default.

```typescript title="src/mastra/signals.ts"
const subscription = await agent.subscribeToThread({
  resourceId: 'user-123',
  threadId: 'thread-abc',
})

void (async () => {
  for await (const chunk of subscription.stream) {
    console.log(chunk)
  }
})()

agent.sendMessage('Use the latest customer note too.', {
  resourceId: 'user-123',
  threadId: 'thread-abc',
  ifIdle: {
    streamOptions: {
      maxSteps: 3,
    },
  },
})
```

Use `attributes` à identify different users dans a shared thread. The attributes sont rendered comme XML so the modèle peut distinguish who said what:

```typescript
agent.sendMessage(
  {
    contents: 'Can we simplify the API surface?',
    attributes: { name: 'Devin', from: 'slack' },
  },
  { resourceId: 'user-123', threadId: 'thread-abc' },
)
```

Le modèle receives this as:

```xml
<user name="Devin" from="slack">Can we simplify the API surface?</user>
```

Use `ifActive.attributes` et `ifIdle.attributes` when the message doit carry different context depending sur whether the thread est currently running:

```typescript title="src/mastra/signals.ts"
agent.sendMessage(
  {
    contents: 'Also cover the edge cases.',
    attributes: { source: 'chat' },
  },
  {
    resourceId: 'user-123',
    threadId: 'thread-abc',
    ifActive: { attributes: { delivery: 'while-active' } },
    ifIdle: { attributes: { delivery: 'new-message' } },
  },
)
```

Lorsque le thread est active, the modèle sees:

```xml
<user source="chat" delivery="while-active">Also cover the edge cases.</user>
```

Lorsque le thread est idle, the modèle sees:

```xml
<user source="chat" delivery="new-message">Also cover the edge cases.</user>
```

The UI sees the message contents et peut also read `attributes` et `metadata` off the signal message pour personnalisé rendering (e.g. showing utilisateur names, avatars, ou platform badges).

Définir `ifIdle.behavior` à `wake` et transmet `ifIdle.streamOptions` when an idle thread doit démarre a nouveau stream avec personnalisé execution options:

```typescript title="src/mastra/signals.ts"
agent.sendMessage('Continue with the next step.', {
  resourceId: 'user-123',
  threadId: 'thread-abc',
  ifIdle: {
    behavior: 'wake',
    streamOptions: {
      maxSteps: 3,
    },
  },
})
```

Renvoie `{ accepted: Promise<SendAgentSignalAccepted>, signal: CreatedAgentSignal, persisted?: Promise<void> }`. `accepted` resolves à decision-time, once Mastra decides what à effectuer avec the message: `{ action: 'wake', runId, output }` when this traite runs the agent (it started ou won the lease à démarre the run), `{ action: 'deliver', runId }` when the message est forwarded onto an existant exécute (including when this traite loses a cross-process wake race), ou `{ action: 'persist' }` / `{ action: 'discard' }` when nothing ran. `runId` est the authoritative id de the exécute that handled the message et est present only sur `wake` et `deliver`. For `persist`/`discard` utilise `result.signal.id` à correlate the stored message. `accepted` resolves pour routing (a generation error sur a `wake` exécute surfaces via `output.consumeStream()`) et rejects only when the message couldn't be routed ou started à tous les (e.g. a misconfigured agent). `persisted` est only present pour `persist` behavior et resolves when Mastra finishes writing the message à memory. On the `wake` action, `output` est the agent stream pour in-process consumption.

### `queueMessage(message, options)`

Queues a utilisateur message pour the next turn sur a thread. Si le thread est active, Mastra waits pour the active exécute à finish, then starts a nouveau exécute avec the queued message. Si le thread est idle, Mastra starts a exécute immediately.

```typescript
agent.queueMessage('Also check whether the tests need updates.', {
  resourceId: 'user-123',
  threadId: 'thread-abc',
})
```

`queueMessage()` accepts the same `message` et `options` shape comme `sendMessage()` et returns `{ accepted: Promise<SendAgentSignalAccepted>, signal: CreatedAgentSignal, persisted?: Promise<void> }`, avec the same `accepted` semantics comme `sendMessage()`.

```typescript
const result = agent.sendSignal(signal, { resourceId, threadId })
ctx.waitUntil(
  result.accepted.then(async accepted => {
    if (accepted.action === 'wake') {
      await accepted.output.consumeStream()
    }
  }),
)
```

Renvoie `{ record: NotificationRecord, decision: NotificationDeliveryDecision, runId?: string, signal?: CreatedAgentSignal, persisted?: Promise<void>, accepted?: Promise<SendAgentSignalAccepted> }`. `record` est the stored inbox record. `decision` est the delivery-policy result. `signal` et `runId` sont present when ingress emits a signal immediately, including the immediate summary emitted pour active high-priority notifications. `persisted` est present when the emitted signal est persisted sans waking an idle thread. `accepted` est present when a signal est emitted et resolves à decision-time, once Mastra decides what à effectuer avec it: `{ action: 'wake', runId, output }` when this traite runs the agent (it started ou won the lease à démarre the run), `{ action: 'deliver', runId }` when the signal est forwarded onto an existant run, ou `{ action: 'persist' }` / `{ action: 'discard' }` when nothing ran. `runId` sur the accepted résultat est present only sur `wake` et `deliver`. On the `wake` action, `output` est the agent stream pour in-process consumption.

Par défaut delivery est priority-aware. `urgent` notifications deliver immediately. `high` notifications deliver immediately when the thread est idle. Lorsque le thread est active, Mastra emits a summary immediately et keeps `deliverAt` pour later full delivery when the thread est idle. `medium` notifications deliver immediately when idle et batch dans summaries when active. `low` notifications batch dans summaries dans both active et idle threads. Idle low-priority summaries reach subscribers sans waking the modèle loop. Pour la version complète flow, visit [Signals](/docs/long-running-agents/signals#notification-signals).

Configurer `notifications.deliveryPolicy` sur the agent when certains notifications doit wait pour a different dispatch window ou summary rollup:

```typescript title="src/mastra/agents/support-agent.ts"
export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user triage updates.',
  model: '__GATEWAY_OPENAI_MODEL__',
  notifications: {
    deliveryPolicy: {
      priorities: {
        urgent: 'deliver',
      },
      decide: ({ record }) => {
        if (record.priority === 'low') {
          return {
            action: 'summarize',
            summaryAt: new Date(Date.now() + 30 * 60 * 1000),
          }
        }
      },
    },
  },
})
```

### `subscribeToThread(options)`

Subscribes à raw stream chunks pour a memory thread. Utilisez ce avant calling `sendMessage()`, `queueMessage()`, ou `sendSignal()`. It lets you affiche stream output et observe signal echoes, including when a signal aborts the active run.

## `generate()` memory options

Pass `memory` when you call `agent.generate()` à choose which conversation thread the exécute doit read depuis et write to. The common shape est `memory: { resource: string, thread: string }`, where `resource` identifies the owner et `thread` identifies the conversation. Consultez [Threads et resources](/docs/memory/message-history#threads-and-resources) pour the concept model.

```typescript title="src/mastra/run.ts"
const response = await agent.generate('What did we decide about retries?', {
  memory: {
    resource: 'user-123',
    thread: 'support-thread-456',
  },
})
```

Utilisez un thread objet when you need à crée ou met à jour thread metadata during the call:

```typescript title="src/mastra/run.ts"
const response = await agent.generate('Continue the support conversation.', {
  memory: {
    resource: 'user-123',
    thread: {
      id: 'support-thread-456',
      title: 'Billing support',
      metadata: { category: 'billing' },
    },
  },
})
```

## Tool hooks

Use `hooks` à exécute logic around every Tool call the agent makes, including assigned tools, memory tools, toolsets, client tools, et workspace tools.

```typescript title="src/mastra/agents/hooked-agent.ts"
import { Agent } from '@mastra/core/agent'

export const agent = new Agent({
  id: 'support-agent',
  name: 'support-agent',
  instructions: 'Help users with their questions.',
  model: '__GATEWAY_OPENAI_MODEL__',
  // highlight-start
  hooks: {
    beforeToolCall: ({ toolName, input }) => {
      console.log(`Running ${toolName}`, input)
    },
    afterToolCall: ({ toolName, output, error }) => {
      console.log(`Finished ${toolName}`, { output, error })
    },
  },
  // highlight-end
})
```

`beforeToolCall` peut short-circuit the Tool call par returning `{ proceed: false, output }`. L’agent skips execution et uses `output` comme the Tool result:

```typescript
const result = await agent.generate('Clean up old records', {
  hooks: {
    beforeToolCall: ({ toolName }) => {
      if (toolName === 'deleteRecord') {
        return { proceed: false, output: { blocked: true } }
      }
    },
  },
})
```

The hook context `metadata` includes `agentId` et `agentName`. Per-execution hooks passed à `generate()` ou `stream()` override matching agent-level hooks. Lorsqu’un [workspace](/reference/workspace/workspace-class) also defines `tools.hooks`, workspace hooks exécute inside the agent hook wrapper.
