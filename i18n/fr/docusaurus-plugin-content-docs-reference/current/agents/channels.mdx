# Canaux

**Added in:** `@mastra/core@1.22.0`

Canaux connecte agents à messaging platforms. Configurer them via the `channels` propriété sur the `Agent` constructor. L’objet you transmet est a `ChannelConfig`. Consultez the [Canaux overview](/docs/capabilities/channels/overview) pour concepts et platform setup instructions.

## Exemple d’utilisation

```typescript title="src/mastra/agents/support-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createSlackAdapter } from '@chat-adapter/slack'
import { createDiscordAdapter } from '@chat-adapter/discord'

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'You are a helpful support assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
  channels: {
    adapters: {
      slack: createSlackAdapter(),
      discord: createDiscordAdapter(),
    },
  },
})
```

## Tool affiche modes

`toolDisplay` controls how Tool calls affiche dans chat. La valeur par défaut `'cards'`
posts a "Running…" card per Tool et edits it avec the result, matching the
behavior dans earlier versions. `'text'` est the same lifecycle mais sans rich
Block Kit, useful pour platforms that don't affiche cards well.

`'timeline'` et `'grouped'` stream Tool state comme inline `task_update` chunks
alongside the agent's text. Ces modes require `streaming: true` et rely on
the chat adapter à affiche the chunks. Slack supports both natively; other
adapters peut affiche a placeholder until they ajoute support. If `streaming` is
disabled, the channel logs a one-time warning et falls back à `'cards'`.

`'hidden'` executes tools silently. Only the typing status indicates work in
progress.

Pass a fonction à `toolDisplay` pour fully personnalisé rendering. La fonction
receives a `ToolDisplayEvent` (`running` / `result` / `error` / `approval`)
and a `ToolDisplayContext` (`{ mode, platform }`); renvoie `{ kind: 'post',
message }` for a discrete post/edit, `{ kind: 'stream', chunk }` à push into
the active streaming widget, ou `undefined` à skip rendering that event.

Par défaut, a stream résultat opens a streaming session when none est active. Set
`openIfEmpty: false` when the chunk only applies à an existant session. Mastra
skips the chunk when aucun session est active. Statique channels ignore this option
and keep their existant plain-text fallback behavior.

```typescript
toolDisplay: event => {
  if (event.kind !== 'running') return undefined

  return {
    kind: 'stream',
    chunk: {
      type: 'task_update',
      id: event.toolCallId,
      title: event.displayName,
      status: 'in_progress',
    },
    openIfEmpty: false,
  }
}
```

Approve/deny prompts (`requireApproval`) always affiche comme a separate card
regardless de mode, car inline task entries can't carry interactive
buttons.

```typescript title="src/mastra/agents/streaming.ts"
import { Agent } from '@mastra/core/agent'
import { createSlackAdapter } from '@chat-adapter/slack'

const agent = new Agent({
  id: 'streaming-agent',
  name: 'Streaming Agent',
  instructions: '...',
  model: '__GATEWAY_OPENAI_MODEL__',
  channels: {
    adapters: {
      slack: {
        adapter: createSlackAdapter(),
        streaming: true, // already the Slack default
        toolDisplay: 'timeline',
      },
    },
  },
})
```

## Personnalisé typing status

Pass a fonction à `typingStatus` à customize the status copy. La fonction is
called once per stream chunk; renvoie a chaîne à définit the status, ou `false` /
`null` / `undefined` à leave the actuel status unchanged. Valeurs renvoyées are
de-duplicated so the platform only sees a call when the status changes.

`defaultTypingStatus` est exported depuis `@mastra/core/channels` so you can
fall back à the built-in defaults pour chunks you don't handle.

```typescript title="src/mastra/agents/custom-typing.ts"
import { Agent } from '@mastra/core/agent'
import { defaultTypingStatus } from '@mastra/core/channels'
import { createDiscordAdapter } from '@chat-adapter/discord'

const agent = new Agent({
  id: 'custom-typing-agent',
  name: 'Custom Typing Agent',
  instructions: '...',
  model: '__GATEWAY_OPENAI_MODEL__',
  channels: {
    adapters: {
      discord: {
        adapter: createDiscordAdapter(),
        typingStatus: (chunk, ctx) => {
          if (chunk.type === 'tool-call' && chunk.payload.toolName === 'searchDocs') {
            return 'is searching docs…'
          }
          return defaultTypingStatus(chunk, ctx)
        },
      },
    },
  },
})
```

## Handlers

Override built-in event handlers. Chaque handler peut be:

- **Omitted**: uses the par défaut Mastra handler (routes the message via the agent et posts the response)
- **`false`**: disables the handler entirely
- **Un function** `(thread, message, defaultHandler) => Promise<void>`: wraps ou replaces the default

```typescript title="src/mastra/agents/custom-handlers.ts"
import { Agent } from '@mastra/core/agent'
import { createSlackAdapter } from '@chat-adapter/slack'

const agent = new Agent({
  id: 'custom-handler-agent',
  name: 'Custom Handler Agent',
  instructions: '...',
  model: '__GATEWAY_OPENAI_MODEL__',
  channels: {
    adapters: {
      slack: createSlackAdapter(),
    },
    handlers: {
      onMention: async (thread, message, defaultHandler) => {
        console.log('Received mention:', message.text)
        await defaultHandler(thread, message)
      },
      onDirectMessage: false,
    },
  },
})
```

The `ChannelHandler` fonction signature:

```typescript
type ChannelHandler = (
  thread: Thread,
  message: Message,
  defaultHandler: (thread: Thread, message: Message) => Promise<void>,
  ctx: ChannelHandlerContext,
) => Promise<void>

type ChannelHandlerContext = {
  mastra?: Mastra
  requestContext: RequestContext
}
```

`ctx.mastra` est the resolved `mastra` instance, so a handler peut reach storage ou autre registered primitives sans being passed an external accessor:

```typescript
onDirectMessage: async (thread, message, defaultHandler, ctx) => {
  const store = await ctx.mastra?.getStorage()?.getStore('memory')
  await defaultHandler(thread, message)
}
```

`ctx.requestContext` est the [`RequestContext`](/docs/server/request-context) pour the exécute this message est concernant à start, built fresh pour every message. Write à it avant calling `defaultHandler` et the valeur reaches the run, alongside the channel entries Mastra adds afterward:

```typescript
onDirectMessage: async (thread, message, defaultHandler, ctx) => {
  ctx.requestContext.set('locale', 'en-GB')
  await defaultHandler(thread, message)
}
```

Anything the exécute reads depuis its requête context peut be decided per message this way, such comme which utilisateur a platform sender maps to.

## Resource ID resolution

Par défaut a channel thread's memory `resourceId` est `${platform}:${message.author.userId}`. The sender owns the memory, scoped per platform. For apps avec a shared identity, such comme unique sign-on (SSO), this splits memory: the same utilisateur gets `feishu:user_123` dans a Feishu DM mais `user_123` sur the web.

Pass `resolveResourceId` à decide memory ownership separately depuis the sender. It runs only when a nouveau thread est created. Reused threads keep their stored `resourceId` et never call the hook, so existant conversations don't depend sur the resolver being available. Renvoyer `ctx.defaultResourceId` à fall back à the built-in behavior.

```typescript title="src/mastra/agents/sso-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createSlackAdapter } from '@chat-adapter/slack'

const agent = new Agent({
  id: 'sso-agent',
  name: 'SSO Agent',
  instructions: '...',
  model: '__GATEWAY_OPENAI_MODEL__',
  channels: {
    adapters: {
      slack: createSlackAdapter(),
    },
    resolveResourceId: async ({ thread, message }) => {
      // DM: share resource-level memory with the web app by using the bare SSO id
      if (thread.isDM) {
        return await resolveSsoUserId(message)
      }
      // Group chat: the conversation owns the memory; the sender stays the actor
      return thread.channelId
    },
  },
})
```

## Thread ID resolution

Par défaut a nouveau channel thread gets a random UUID comme its internal Mastra thread id. Pass `resolveThreadId` à pick the id yourself: pour example, give the thread the same id comme the session it belongs to, matching how your app names threads it creates itself.

The hook runs après `resolveResourceId`, so the resolved owner est disponible sur the context. Like `resolveResourceId` it runs only when a nouveau thread est created: reused threads keep their stored id et never call the hook. La valeur renvoyée id doit be unique across the memory store. If it already belongs à an existant thread, Mastra logs a warning et uses a generated id instead so the existant thread est never overwritten. Renvoyer `ctx.defaultThreadId` à keep the built-in behavior.

```typescript title="src/mastra/agents/session-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createSlackAdapter } from '@chat-adapter/slack'

const agent = new Agent({
  id: 'session-agent',
  name: 'Session Agent',
  instructions: '...',
  model: '__GATEWAY_OPENAI_MODEL__',
  channels: {
    adapters: {
      slack: createSlackAdapter(),
    },
    // Owner: a session id resolved from the sender's linked account
    resolveResourceId: async ctx => resolveSessionId(ctx),
    // Thread id: align with the session id so app URLs that address
    // threads by session id resolve channel-created threads too
    resolveThreadId: ({ resourceId, defaultThreadId }) => {
      return isSessionId(resourceId) ? resourceId : defaultThreadId
    },
  },
})
```

## Inline media

Contrôle which attachment types (images, video, PDFs, etc.) sont sent comme file parts à the model. Types that don't match sont described comme text summaries so the agent knows concernant the file sans crashing models that reject unsupported types.

La valeur par défaut (`['image/png', 'image/jpeg', 'image/webp', 'application/pdf']`) matches the formats pris en charge par major vision models. Override `inlineMedia` à expand the liste (e.g. `['image/*', 'audio/*']`) ou replace it entirely avec a predicate function.

Pris en charge glob patterns:

| Pattern | Matches |
| - | - |
| `image/*` | Tous les image types (`image/png`, `image/jpeg`, etc.) |
| `video/*` | Tous les video types |
| `*` ou `*/*` | Tous les types |
| `application/pdf` | Exact type match |

For platforms avec private CDNs (e.g. Slack), attachments sont fetched avec authenticated credentials depuis the Chat SDK. For platforms avec public CDNs (e.g. Discord), the URL est passed directly à the model.

## Inline links

Promotes URLs found dans message text à file parts so the modèle peut traite linked content instead de seeing raw URL text. Chaque entry peut be a chaîne (domain pattern) ou an objet avec a forced mime type.

**String entries** match a domain et perform a HEAD requête à detect the Content-Type. The resolved type est checked against `inlineMedia` et only matching types become file parts.

**Object entries** match a domain et force a specific mime type, skipping the HEAD requête et bypassing the `inlineMedia` check. Ce est useful pour sites like YouTube where a HEAD requête returns `text/html`, mais the modèle treats the URL comme video content.

```typescript
type InlineLinkEntry =
  | string // Domain pattern (HEAD determines mime type)
  | { match: string; mimeType: string } // Domain + forced mime type (skips HEAD)
```
