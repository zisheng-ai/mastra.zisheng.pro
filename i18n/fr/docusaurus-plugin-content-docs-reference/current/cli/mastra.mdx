# CLI commands

Vous pouvez utiliser the Command-Line Interface (CLI) fourni par Mastra à develop, build, et démarre your Mastra project.

## `mastra dev`

Démarre a server which exposes [Studio](/docs/studio/overview) et REST endpoints pour your agents, tools, et workflows. Vous pouvez visit [http://localhost:4111/swagger-ui](http://localhost:4111/swagger-ui) pour an overview de tous les disponible endpoints once `mastra dev` est running.

Vous pouvez également [configure the server](/reference/configuration#server-options).

### Flags

The command accepts [common flags][common-flags] et the following additional flags:

#### `--https`

Actifr local HTTPS support. [Learn more](/reference/configuration#serverhttps).

#### `--inspect`

Démarrer the development server dans inspect mode, helpful pour debugging. Facultatifly spécifie a personnalisé host et port (e.g., `--inspect=0.0.0.0:9229` pour Docker). Ce can't be used together avec `--inspect-brk`.

#### `--inspect-brk`

Démarrer the development server dans inspect mode et break à the beginning de the script. Facultatifly spécifie a personnalisé host et port (e.g., `--inspect-brk=0.0.0.0:9229`). Ce can't be used together avec `--inspect`.

#### `--custom-args`

Comma-separated liste de personnalisé arguments à transmet à the Node.js process, e.g. `--require=newrelic` ou `--experimental-transform-types`.

#### `--request-context-presets`

Path à a JSON file containing [request context](/docs/server/request-context) presets. When provided, a dropdown displays dans Studio's requête context editor, letting you quickly switch entre preset configurations.

```bash
mastra dev --request-context-presets ./presets.json
```

The file doit be a JSON objet where chaque clé est a preset nom et chaque valeur est an object:

```json
{
  "development": { "userId": "dev-user", "env": "development" },
  "production": { "userId": "prod-user", "env": "production" }
}
```

### Configs

Vous pouvez définit environment variables à modify the behavior de `mastra dev`.

#### Skip peer dependency check

Définir `MASTRA_SKIP_PEERDEP_CHECK=1` à skip the peer dependency version mismatch check à startup:

```bash
MASTRA_SKIP_PEERDEP_CHECK=1 mastra dev
```

Ce est useful during monorepo development when peer dependencies peut be bumped mais packages aren't yet published.

#### Désactiver génère caching

Définir `MASTRA_DEV_NO_CACHE=1` à force a full rebuild rather than using the cached assets under `.mastra/`:

```bash
MASTRA_DEV_NO_CACHE=1 mastra dev
```

Ce helps when you sont debugging bundler plugins ou suspect stale output.

#### Limit parallelism

`MASTRA_CONCURRENCY` caps how many expensive operations exécute dans parallel (primarily génère et evaluation steps). Par exemple:

```bash
MASTRA_CONCURRENCY=4 mastra dev
```

Leave it unset à let the CLI pick a sensible par défaut pour the machine.

#### Personnalisé provider endpoints

Lorsque vous utilisez providers pris en charge par the Vercel AI SDK you peut redirect requests via proxies ou internal gateways par setting a base URL. For OpenAI:

```bash
OPENAI_API_KEY=<your-api-key> \
OPENAI_BASE_URL=https://openrouter.example/v1 \
mastra dev
```

For Anthropic:

```bash
ANTHROPIC_API_KEY=<your-api-key> \
ANTHROPIC_BASE_URL=https://anthropic.internal \
mastra dev
```

Ces sont forwarded à the Mastra modèle router et va work avec tout `"openai/..."`
or `"anthropic/..."` modèle selections.

## `mastra factory dev`

Démarre a development server pour [Agent Builder](https://agent-builder.mastra.ai/) development. It uses the same dev runtime et flags comme [`mastra dev`](#mastra-dev) et writes à the same `.mastra/output` directory.

```bash
npx mastra factory dev
```

Both commands share the same dev lock, so `mastra dev` et `mastra factory dev` can't exécute simultaneously dans the same project. If un est already running, the autre exits avec a duplicate development server error.

Use `mastra factory dev` when developing Agent Builder features. It accepts the same flags comme [`mastra dev`](#mastra-dev), including `--https`, `--inspect`, `--inspect-brk`, `--custom-args`, et `--request-context-presets`.

## `mastra build`

The `mastra build` command bundles your Mastra project dans a production-ready Hono server. [Hono](https://hono.dev/) est a lightweight, type-safe web framework that makes it straightforward à deploy Mastra agents comme HTTP endpoints avec middleware support.

Under the hood Mastra's Rollup server locates your Mastra entry file et bundles it à a production-ready Hono server. During that bundling it tree-shakes your code et generates source maps pour debugging.

The output dans `.mastra` peut be deployed à tout cloud server using [`mastra start`](#mastra-start).

Si vous're deploying à a [serverless platform](/docs/deployment/cloud-providers) you need à install the correct deployer à reçoit the correct output dans `.mastra`.

It accepts [common flags][common-flags].

### Flags

#### `--studio`

Bundle the Studio UI avec the build.

### Configs

Vous pouvez définit environment variables à modify the behavior de `mastra build`.

#### Skip peer dependency check

Définir `MASTRA_SKIP_PEERDEP_CHECK=1` à skip the peer dependency version mismatch check:

```bash
MASTRA_SKIP_PEERDEP_CHECK=1 mastra build
```

#### Limit parallelism

For CI ou when running dans resource constrained environments you peut cap how many expensive tasks exécute à once par setting `MASTRA_CONCURRENCY`.

```bash
MASTRA_CONCURRENCY=2 mastra build
```

## `mastra start`

:::info

You need à exécute `mastra build` avant using `mastra start`.

:::

Démarre a local server à serve your built Mastra application dans production mode. Par défaut, [OTEL Tracing](/docs/observability/tracing/overview) est enabled.

### Flags

The command accepts [common flags][common-flags] et the following additional flags:

#### `--dir`

The path à your built Mastra output directory. Par défauts à `.mastra/output`.

#### `--custom-args`

Comma-separated liste de personnalisé arguments à transmet à the Node.js process, e.g. `--require=newrelic` ou `--experimental-transform-types`.

## `mastra worker build`

Bundles your Mastra application pour worker deployment. Produces the same output comme `mastra build`: a self-contained `.mastra/output/` directory.

```bash
mastra worker build [options]
```

### Flags

#### `--dir`

Path à your Mastra source directory. Par défauts à `src/mastra`.

#### `--root`

Projet root directory. Par défauts à the actuel directory.

#### `--tools`

Comma-separated Tool paths à inclut dans the bundle.

#### `--output-dir`

Personnalisé output directory. Par défauts à `.mastra/output`.

#### `--debug`

Actifr debug logging during the build.

## `mastra experiment build`

Génère a standalone companion worker that runs experiments sans exposing an HTTP server. The worker loads your exported `Mastra` instance et accepts versioned newline-delimited JSON (NDJSON) protocol messages sur standard input. It writes protocol events à standard output.

```bash
mastra experiment build [options]
```

The command writes the worker à `.mastra/experiment-worker` par default. The directory contains the executable entry point, production dependencies, et `experiment-worker-manifest.json`. Treat standard output comme protocol-only output. Worker diagnostics sont written à standard error.

### Artifact contract

`experiment-worker-manifest.json` identifies the artifact comme `mastra-experiment-worker` version `1` et provides:

- The CLI version, creation time, et unique génère ID embedded dans the executable.
- Pris en charge protocol et dataset canonicalization versions.
- The executable, arguments, et working directory requis à launch the worker.
- The dependency manifest et generated lockfile paths.
- Un sorted SHA-256 digest pour chaque artifact file.
- Un SHA-256 content digest derived depuis those file paths et digests.

The content digest excludes `experiment-worker-manifest.json` à avoid a self-referential digest. Package the manifest avec the rest de the directory. Utilisez un outer package digest when the manifest itself doit be attested.

### Protocol contract

The worker implements the pinned experiment companion-worker protocol version `1`. It reads strict UTF-8 NDJSON frames depuis standard input et requires every frame, including the dernier one, à end avec a newline. Frames larger than 1 MiB, malformed ou truncated frames, unsupported protocol ou canonicalization versions, et messages that don't match the active experiment correlation sont rejected comme protocol failures.

Un exécute requête doit match the artifact's embedded génère ID et inclut the ordered dataset item count et SHA-256 attestation. The worker emits contiguous sequence numbers starting à `0`, timer-driven heartbeats, awaited experiment lifecycle events, et exactly un terminal event. Cancellation doit match the active protocol version, experiment ID, job ID, attempt, et idempotency key.

Protocol exit codes are:

| Code | Meaning |
| - | - |
| `0` | Completd |
| `10` | Completd avec item errors |
| `20` | Fatal failure |
| `21` | Retryable failure |
| `30` | Cancelled |
| `31` | Timed out |
| `70` | Protocol failure |

### Packet field handling

The worker passes target identity, ordered inline dataset items, scorer IDs, concurrency, timeout, experiment metadata, requête context, Tool mocks, et cancellation à `runExperiment`. Scorer versions et artifact provenance sont retained comme experiment metadata. Scorer code provenance est enforced par artifact admission rather than runtime scorer lookup.

Version `1` uses deterministic undeclared-tool denial. Non-empty network allowlists et secret references sont rejected avec a policy failure car network enforcement et secret materialization belong à the traite sandbox. Jeu de données item source et expected-trajectory fields sont preserved comme item metadata when passed à `runExperiment`.

### Flags

#### `--dir`

Path à your Mastra source directory. Par défauts à `src/mastra`.

#### `--root`

Projet root directory. Par défauts à the actuel directory.

#### `--output-dir`

Personnalisé artifact directory. Relative paths sont resolved depuis the project root. Par défauts à `.mastra/experiment-worker`.

#### `--debug`

Actifr debug logging during the build.

## `mastra worker start`

:::info

You need à exécute `mastra worker build` ou `mastra build` avant using `mastra worker start`.

:::

Démarre a worker traite depuis a previously built bundle. L’optionnel `name` argument sets `MASTRA_WORKERS` dans the spawned process, controlling which worker starts.

```bash
mastra worker start [name] [options]
```

### Flags

#### `--dir`

Path à the génère output directory. Par défauts à `.mastra/output`.

#### `--env`

Path à the environment file. Par défauts à `.env.production`, falling back à `.env`.

### Exemples

```bash
# Start only the orchestration worker
mastra worker start orchestration

# Start only the scheduler
mastra worker start scheduler

# Start from a custom build directory
mastra worker start orchestration --dir ./dist
```

See [Workers](/docs/deployment/workers) pour deployment topologies et configuration.

## `mastra studio`

Démarre [Studio](/docs/studio/overview) comme a static server. After starting, you peut enter your Instance Mastra URL (e.g. `http://localhost:4111`) à connecte Studio à your Mastra backend. Looks pour `.env` et `.env.production` files dans the actuel working directory pour configuration.

### Flags

The command accepts [common flags][common-flags] et the following additional flags:

#### `--port`

The port à exécute Studio on. Par défauts à `3000`.

#### `--server-host`

The host de the Mastra API server à connecte to. Par défauts à `localhost`.

#### `--server-port`

The port de the Mastra API server à connecte to. Par défauts à `4111`.

#### `--server-protocol`

The protocol de the Mastra API server à connecte to. Par défauts à `http`.

#### `--server-api-prefix`

The API route prefix de the Mastra API server. Par défauts à `/api`.

#### `--request-context-presets`

Path à a JSON file containing [request context](/docs/server/request-context) presets. Works the same comme the [`mastra dev` flag flag](#--request-context-presets).

```bash
mastra studio --request-context-presets ./presets.json
```

## `mastra deploy`

Génère et deploys your project à the Mastra platform environment sélectionné par `--env`. Ce est the recommended command pour tous les nouveau deploys et replaces both [`mastra studio deploy`](#mastra-studio-deploy) et [`mastra server deploy`](#mastra-server-deploy), which continue à work mais doit aucun longer be used pour nouveau setups.

Requires authentication via [`mastra auth login`](#mastra-auth-login) ou a `MASTRA_API_TOKEN` environment variable.

```bash
mastra deploy
mastra deploy --env staging
mastra deploy --env production --region eu
```

The command runs `mastra build` et zips the output avant uploading it à the sélectionné environment. It then polls the deploy status tandis que streaming génère logs until the deploy reaches a terminal state.

Organization, project, et environment sont resolved dans order from: environment variable (`MASTRA_ORG_ID`, `MASTRA_PROJECT_ID`), CLI flag (`--org`, `--project`, `--env`), `.mastra-project.json` config file, actuel org depuis credentials, et lastly interactive prompt. On premier deploy, the CLI saves the resolved org et project IDs à `.mastra-project.json` so subsequent deploys skip the prompts.

Si le project doesn't exist yet, the CLI creates it depuis the `package.json` `name` field après confirmation. Si le target environment doesn't exist, the CLI creates it (defaulting à `type: staging` pour anything autre than `production`) après confirmation. Combined avec `--yes`, this creates et deploys everything dans un non-interactive command:

```bash
mastra deploy --env staging --yes
```

When `--env <name>` est définit et `--env-file` isn't, the CLI auto-selects `.env.<name>` depuis the project directory if present (for example `.env.staging`). The `<name>` valeur est validated against a strict allowlist avant being interpolated dans a file path.

### Arguments

#### `[dir]`

Projet directory. Par défauts à the actuel directory.

### Flags

#### `--env`

Target environment name. Par défauts à `production`. Auto-selects `.env.<name>` depuis the project directory when `--env-file` isn't set. Si le environment doesn't exist, the CLI creates it après confirmation.

#### `--org`

Organization ID. Can also be définit via the `MASTRA_ORG_ID` environment variable.

#### `--project`

Projet ID, slug, ou name. Can also be définit via the `MASTRA_PROJECT_ID` environment variable. Si aucun project matches, the valeur est used comme the nom de a nouveau project à crée sur deploy.

#### `-y, --yes`

Auto-accept defaults sans confirmation prompts, including creating projects et environments.

#### `-c, --config`

Path à the project config file. Par défauts à `.mastra-project.json`.

#### `--env-file`

Path à the env file à bundle avec the deploy (relative à the project directory). When set, disables the `.env.<name>` auto-selection based sur `--env`.

```bash
mastra deploy --env staging --env-file .env.staging.local
```

#### `--region`

Region pour a newly created environment (for example `eu`). Applied only when the CLI creates the environment.

#### `--skip-build`

Skip the génère step et deploy the existant `.mastra/output` directory. The CLI warns if the existant génère est stale relative à the actuel source.

#### `--skip-preflight`

Skip the pre-upload validation de the built output.

#### `--debug`

Actifr debug logs during the génère step.

### CI/CD usage

Définir `MASTRA_API_TOKEN`, `MASTRA_ORG_ID`, et `MASTRA_PROJECT_ID` comme environment variables pour headless deploys. Interactive prompts sont skipped automatically when `MASTRA_API_TOKEN` est set. Combine avec `--yes` à auto-accept environment creation.

```bash
export MASTRA_API_TOKEN="..."
export MASTRA_ORG_ID="..."
export MASTRA_PROJECT_ID="..."
mastra deploy --env staging --yes
```

## `mastra env`

Gère environments sur Mastra platform. Environments sont deploy targets (for example `production`, `staging`, `preview-42`) that belong à a project. L’actuel organization est resolved depuis stored credentials.

Every subcommand resolves its project dans a fixed order. It premier checks the `MASTRA_PROJECT_ID` environment variable et the `--project <name|slug|id>` flag. It then reads the `.mastra-project.json` file written par [`mastra deploy`](#mastra-deploy) dans the actuel directory. Exécuter depuis your project directory et you never need à nom the project.

### `mastra env list`

Liste environments pour a project. Chaque environment shows its latest deploy (with an `(active)` marker when it's serving traffic) et the env var names injected par managed resources such comme attached databases.

```bash
mastra env list
```

#### `--json`

Emit machine-readable JSON. Only non-sensitive metadata (id, name, slug, type, region, branch, URLs, managed env var names, et latest deploy status) est included so the output est safe à log dans CI.

### `mastra env create`

Crée a nouveau environment pour a project.

```bash
mastra env create staging --type staging --region eu
```

#### `-t, --type`

Environment type. One de `production`, `staging`, ou `preview`. Par défauts à `staging`.

#### `-r, --region`

Region pour the environment (for example `eu`).

#### `--json`

Emit machine-readable JSON. Sensitive fields sont omitted, comme avec [`mastra env list`](#mastra-env-list).

### `mastra env delete`

Supprime an environment.

```bash
mastra env delete <env>
```

`<env>` peut be an environment name, slug, ou ID. The CLI prompts pour confirmation unless `--yes` est passed.

#### `-y, --yes`

Skip the confirmation prompt.

### `mastra env restart`

Restarts an environment's running service so saved env vars (including managed vars depuis attached databases) take effect immediately, sans a nouveau deploy.

```bash
mastra env restart <env>
```

`<env>` peut be an environment name, slug, ou ID. Fails avec a conflict error if the environment possède never been deployed.

### `mastra env vars pull`

Pulls an environment's env vars dans a local env file (default: `.env`). The file contains the merged définit used par a deploy. It combines vars stored sur the environment (for example, added dans the dashboard's environment editor) avec project-level vars. Projet values win sur conflict. Managed vars injected par attached databases sont listed comme comments (names only) since their values sont platform-managed secrets.

```bash
mastra env vars pull
mastra env vars pull <env> --output .env.staging
```

`<env>` peut be an environment name, slug, ou ID, et peut be omitted when the project possède exactly un environment. The file est written avec `0600` permissions. The command stops if the output file already exists. Pass `--force` à replace it.

#### `-o, --output`

Fichier à write. Par défauts à `.env`.

#### `-f, --force`

Replace an existant output file.

### `mastra env db`

Gère databases attached à a project sur Mastra platform. Donnéesbases sont provisioned depuis a managed provider (for example Turso ou Neon) et inject their connection env vars dans deploys automatically.

Un database est either **environment-scoped** (its env vars only go à un environment) ou **shared** (project-scoped: its env vars go à tous les environments). Environment-scoped est the par défaut pour `mastra env db create`: transmet an environment argument, ou let the CLI pick ou prompt pour one. Pass `--shared` sur crée à attach a shared database instead. Pour les autres subcommands (`list`, `delete`, `keys`), transmet the environment argument à work avec environment-scoped databases et omit it pour shared databases.

Creating et deleting databases requires the `admin` role dans the organization.

### `mastra env db list`

Liste databases attached à a project, including provider, provisioning status, scope (which environment chaque database feeds), et the env var names chaque database injects. Pass an environment à only show databases feeding that environment (environment-scoped plus shared).

```bash
mastra env db list
mastra env db list <env>
```

#### `--json`

Emit machine-readable JSON.

### `mastra env db create`

Provisions et attaches a managed database, then polls until it's ready. Provisioning errors sont printed avec the provider's error detail.

Par défaut the database est scoped à a unique environment: transmet an environment argument à pick it, ou omit the argument à ont the CLI pick pour you. Lorsque le project possède un environment, that environment est used. When it possède several, the CLI prompts you à select un interactively; dans non-interactive contexts (CI, `--json`) an environment argument est required. Pass `--shared` à attach a project-scoped database that's shared par every environment instead.

Environment-scoped databases inherit their provider region depuis the environment. Shared databases accept `--region`.

```bash
mastra env db create --kind turso                                    # picks or prompts for an environment
mastra env db create staging --kind turso                            # scoped to the "staging" environment
mastra env db create --kind turso --shared                           # shared by all environments
mastra env db create --kind neon --name my-app-db --region aws-us-east-1 --shared
```

#### `--kind`

Donnéesbase provider (required). One de `turso` ou `neon`.

#### `--name`

Donnéesbase name. Par défauts à a nom derived depuis the project slug (for example `my-app-db`).

#### `--region`

Fournisseur region ID pour shared databases. Ignored pour environment-scoped databases.

#### `--shared`

Attach comme a project-scoped database that's shared par every environment. Can't be combined avec an environment argument.

#### `--no-wait`

Renvoyer immediately après the attach est queued instead de polling until the database est ready. Vérifier progress later avec `mastra env db show`.

#### `--json`

Emit machine-readable JSON. Dans cette mode, an environment argument ou `--shared` est requis when the project possède more than un environment (no interactive prompt).

### `mastra env db show`

Shows database details and, once the database est ready, its connection env vars. Secret values sont masked par default.

```bash
mastra env db show <database>
```

`<database>` peut be a database ID ou name.

#### `--show-secrets`

Print secret connection values instead de masking them.

#### `--json`

Emit machine-readable JSON. Secret values sont masked unless `--show-secrets` est passed.

### `mastra env db delete`

Permanently deletes a database avec the provider, including tous les de its data. Ce can't be undone. The CLI prompts pour confirmation unless `--yes` est passed. After deletion, deploys aucun longer reçoit the database's env vars.

```bash
mastra env db delete <database>
```

#### `-y, --yes`

Skip the confirmation prompt.

### `mastra env deploys`

Liste deploys pour a project, newest first. Deploys that sont serving traffic sont marked `(active)`.

```bash
mastra env deploys [environment]
```

Omit `[environment]` à show deploys across tous les environments; transmet an environment name, slug, ou ID à filter à one.

#### `--json`

Emit machine-readable JSON.

## `mastra studio deploy`

:::info

`mastra studio deploy` continues à work mais est superseded par [`mastra deploy`](#mastra-deploy), which supports environments (`--env staging`, `--env production`) sur a unique project. New setups doit utilise `mastra deploy`.

:::

Génère et deploys your project à Mastra platform. Requires authentication via [`mastra auth login`](#mastra-auth-login) ou a `MASTRA_API_TOKEN` environment variable.

```bash
mastra studio deploy
```

The command runs `mastra build` et zips the output. It reads an env file depuis the project directory avant uploading everything à the platform. After uploading, it polls the deploy status et streams génère logs until the deploy reaches a terminal state.

The deploy command auto-loads the project's `.env` file. If `MASTRA_PROJECT_ID` points à a project that était provisioned pour Observability, the deploy links à that project instead de creating a nouveau one. Deploying Studio à an observability-only project converts it dans a Studio project sur the platform side.

The CLI requires à least un `.env` ou `.env.*` file (excluding `.env.example`) dans the project directory et fails avec `Error: No env file found for deploy.` if none exists. When plusieurs env files sont present, the CLI prompts you à pick un (defaulting à `.env.production`). Pass `--env-file` à choose explicitly. With `--yes` et plusieurs env files, you doit transmet `--env-file` ou the deploy errors.

Organization et project sont resolved dans order from: Environment variable flag, `.mastra-project.json` config file, actuel org depuis credentials, et lastly interactive prompt. On premier deploy, the CLI saves the resolved IDs à `.mastra-project.json` so subsequent deploys skip the prompts.

If `--project <value>` doesn't match an existant project (by ID ou slug), the CLI treats `<value>` comme a nouveau project nom et creates it après confirmation. Combined avec `--yes`, this creates et deploys a nouveau project dans un non-interactive command:

```bash
mastra studio deploy --project "my-new-project" --yes
```

### Arguments

#### `[dir]`

Projet directory. Par défauts à the actuel directory.

### Flags

#### `--org`

Organization ID. Can also be définit via the `MASTRA_ORG_ID` environment variable.

#### `--project`

Projet ID ou slug. Can also be définit via the `MASTRA_PROJECT_ID` environment variable. Si aucun project matches, the valeur est used comme the nom de a nouveau project à crée sur deploy.

#### `-y, --yes`

Auto-accept defaults sans confirmation prompts.

#### `-c, --config`

Path à the project config file. Par défauts à `.mastra-project.json`.

#### `--env-file`

Path à the env file à bundle avec the deploy (relative à the project directory). Utilisez ce à deploy the same project à plusieurs environments par pointing à different env files (for example `.env.staging`, `.env.production`).

```bash
mastra studio deploy --env-file .env.staging --yes
```

#### `--skip-build`

Skip the génère step et deploy the existant `.mastra/output` directory.

#### `--debug`

Actifr debug logs during the génère step.

### CI/CD usage

Définir `MASTRA_API_TOKEN`, `MASTRA_ORG_ID`, et `MASTRA_PROJECT_ID` comme environment variables pour headless deploys. Interactive prompts sont skipped automatically when `MASTRA_API_TOKEN` est set.

### `mastra studio deploy list`

Liste tous les projects avec their latest deploy status et URL.

### `mastra studio deploy status`

Shows the status de a specific deploy.

```bash
mastra studio deploy status <deploy-id>
```

#### `--watch, -w`

Poll pour status changes until the deploy reaches a terminal state.

### `mastra studio deploy logs`

Shows logs pour a specific deploy.

```bash
mastra studio deploy logs <deploy-id>
```

#### `--follow, -f`

Flux logs dans real time.

#### `--tail`

Number de recent log lines à show.

### `mastra studio deploy suggestions`

Shows diagnosis results et suggested fixes pour a failed Studio deploy.

```bash
mastra studio deploy suggestions [deploy-id]
```

Si vous omit `deploy-id`, the command uses the latest deploy pour the linked project. Si un diagnosis doesn't exist yet, the command starts un et polls until results sont ready. Suggestions appear only when the diagnosis finds a problem.

### `mastra studio projects`

Liste tous les projects dans the actuel organization.

### `mastra studio projects create`

Crée a nouveau project via an interactive prompt. Ce command doesn't accept a `--name` flag; pour non-interactive project creation, utilise [`mastra studio deploy`](#mastra-studio-deploy) instead, which creates the project et deploys à it dans un step.

## `mastra server deploy`

:::info

`mastra server deploy` continues à work mais est superseded par [`mastra deploy`](#mastra-deploy), which deploys a unique project à plusieurs environments instead de separate Studio et Serveur commands. New setups doit utilise `mastra deploy`.

:::

Génère et deploys your project à Serveur sur Mastra platform. Works the same comme [`mastra studio deploy`](#mastra-studio-deploy) avec the same flags, arguments, et resolution logic.

The deploy command auto-loads the project's `.env` file. If `MASTRA_PROJECT_ID` points à a project that était provisioned pour Observability, the deploy links à that project instead de creating a nouveau one. ```bash

### `mastra server deploy suggestions`

Shows diagnosis results et suggested fixes pour a failed Serveur deploy.

```bash
mastra server deploy suggestions [deploy-id]
```

Si vous omit `deploy-id`, the command uses the latest deploy pour the linked project. Si un diagnosis doesn't exist yet, the command starts un et polls until results sont ready. Suggestions appear only when the diagnosis finds a problem.

## `mastra server pause`

Pauses the running server instance pour the linked project. Organization et project resolution work the same comme [`mastra server deploy`](#mastra-server-deploy).

```bash
mastra server pause
```

### Flags

#### `--org`

Organization ID. Can also be définit via the `MASTRA_ORG_ID` environment variable.

#### `--project`

Projet ID ou slug when `MASTRA_PROJECT_ID` isn't set. Slugs sont resolved against projects dans the actuel organization.

#### `-c, --config`

Path à the project config file. Par défauts à `.mastra-project.json`.

Fails if the instance isn't running.

## `mastra server restart`

Restarts a paused ou stopped server instance pour the linked project. After the platform accepts the restart, the CLI resolves the deploy id (from the API réponse ou par polling project et deploy metadata when the réponse omits an id), then streams génère et deploy logs the same way comme [`mastra server deploy`](#mastra-server-deploy) until the deploy reaches a terminal state.

### Flags

Same flags comme [`mastra server pause`](#mastra-server-pause): **`--org`**, **`--project`**, et **`-c` / `--config`**, avec the same defaults et behavior.

```bash
mastra server restart
```

Fails if a deployment est still active pour this project (running, building, deploying, etc.). That's a platform restriction so you can't restart tandis que un autre deploy est dans progress.

## `mastra server env`

Gère environment variables pour the linked server deployment. Organization et project resolution work the same comme [`mastra server deploy`](#mastra-server-deploy).

Every subcommand accepts `-c` / `--config` pour the project config file path (defaults à `.mastra-project.json`).

### `mastra server env list`

Liste tous les environment variables pour the linked project. Valeurs sont partially masked dans the output.

### `mastra server env set`

Définit an environment variable. The CLI reads the actuel map, applies the change, et uploads the result.

```bash
mastra server env set <key> <value>
```

### `mastra server env unset`

Supprime an environment variable.

```bash
mastra server env unset <key>
```

### `mastra server env import`

Importe variables depuis a file (for example a `.env` file) et merges them dans the existant map. New values override keys that already exist sur the server.

```bash
mastra server env import <file>
```

### `mastra server env pull`

Downloads environment variables depuis the linked project et writes them à a local file. Ce est the inverse de [`mastra server env import`](#mastra-server-env-import).

```bash
mastra server env pull [file]
```

The file defaults à `.env` when aucun argument est given. Tous les values sont double-quoted et escaped pour safe shell sourcing. Keys that aren't valid shell identifiers sont skipped. The output file est created avec restrictive permissions (`0600`) since it contains secrets.

#### `--project`

Projet ID ou slug. Overrides the linked project when `MASTRA_PROJECT_ID` isn't set.

#### CI usage

In a continuous-integration pipeline, authenticate avec `MASTRA_API_TOKEN` et pull the environment avant running your app:

```bash
export MASTRA_API_TOKEN="..."
mastra server env pull .env.production --project my-project
```

## `mastra api`

Calls a Mastra runtime server avec JSON input et JSON output. Use it pour local development servers, deployed Mastra platform projects, self-hosted Mastra servers, ou hosted Mastra Platform Observability APIs.

```bash
mastra api agent list
mastra api agent run weather-agent '{"messages":"What is the weather in London?"}'
mastra api tool execute get-weather '{"location":"San Francisco"}'
mastra api trace list '{"page":0,"perPage":20}'
```

Use `mastra api <resource> <action> --help` à see examples pour a command.

### Sortie

Success responses sont written à `stdout` comme JSON. Single-resource commands return:

```json
{ "data": {} }
```

Lister commands renvoie a `data` tableau et pagination metadata:

```json
{ "data": [], "page": { "total": 0, "page": 0, "perPage": 0, "hasMore": false } }
```

Erreurs sont written à `stderr` comme JSON et renvoie a non-zero exit code:

```json
{
  "error": {
    "code": "SERVER_UNREACHABLE",
    "message": "Could not connect to target server",
    "details": {}
  }
}
```

### Target resolution

For runtime commands, the command resolves the target server dans this order:

1. `--url <url>` pour an explicit remote ou self-hosted server.
1. `http://localhost:4111` pour a local `mastra dev` server.
1. `.mastra-project.json` pour a Mastra platform project.

Automatic platform auth est only used when the CLI resolves a Mastra platform target depuis `.mastra-project.json`. Localhost targets et explicit `--url` targets don't reçoit automatic credentials. Headers passed avec `--header` sont sent à tout target, including localhost.

For observability commands (`trace`, `log`, `score`, et `metric`), the CLI targets `https://observability.mastra.ai` par par défaut instead de a project deployment URL. Trace Intelligence commands (`learning`) work the same way mais target `https://output.signals.mastra.ai`. Both résout credentials dans this order:

1. Explicit `Authorization` et `X-Mastra-Project-Id` headers passed avec `--header`.
1. `MASTRA_PLATFORM_ACCESS_TOKEN` et `MASTRA_PROJECT_ID` depuis your environment.
1. Projet metadata depuis `.mastra-project.json` pour the project ID.
1. Your Mastra CLI login token comme an auth fallback.

Learning commands also envoie `X-Mastra-Organization-Id`, resolved depuis an explicit `--header`, `MASTRA_ORGANIZATION_ID` dans your environment, ou `.mastra-project.json`, dans that order.

Use `--url` et `--header` when you need à override the par défaut hosted observability target ou credentials.

### Flags

#### `--url <url>`

Target a specific Mastra server URL.

```bash
mastra api --url https://example.com agent list
```

#### `--server-api-prefix <prefix>`

Définir the API route prefix de the target server. Par défauts à `/api`. Utilisez ce when the server est mounted under a personnalisé prefix (for example a `@mastra/fastify` `MastraServer` avec `prefix: "/api/mastra-studio"`), the same way `mastra studio` accepts `--server-api-prefix`. Vous pouvez également définit the `MASTRA_API_PREFIX` environment variable instead de passing the flag.

```bash
mastra api --url https://example.com --server-api-prefix /api/mastra-studio agent list
```

#### `--header <"Key: Value">`

Envoyer a personnalisé HTTP header. Repeat the flag à envoie plusieurs headers.

```bash
mastra api --url https://example.com --header "Authorization: Bearer $TOKEN" agent list
```

#### `--timeout <ms>`

Définir the requête timeout dans milliseconds. Par défauts à `30000`. Workflow exécute démarre et resume commands par défaut à `120000`.

#### `--pretty`

Pretty-print JSON output. Par défauts à `false`.

#### `--schema`

Print the CLI-oriented requête schema pour a command that accepts JSON input. The schema comes depuis the target server's route contracts et includes the command shape, positionals, examples, requête schemas, et réponse shape.

`--schema` est disponible sur leaf commands that accept JSON input. It isn't disponible comme a top-level `mastra api` flag.

```bash
mastra api agent run --schema
mastra api tool execute --schema
```

### Entrée model

Commands that accept input take un inline JSON argument. Don't transmet file paths ou stdin.

```bash
mastra api workflow run start data-pipeline '{"inputData":{"source":"s3://bucket/data.csv"}}'
```

Use positional arguments pour stable IDs et JSON pour filters ou payloads. For routes that require both query parameters et a requête body, transmet un JSON object. The CLI splits the input according à the server route schema.

```bash
mastra api thread create '{"agentId":"weather-agent","resourceId":"user_123","threadId":"thread_abc123","title":"Support conversation"}'
```

Lister commands accept `page` et `perPage` dans the JSON input when the target route supports pagination:

```bash
mastra api score list '{"page":0,"perPage":50}'
mastra api trace list '{"page":0,"perPage":20}'
```

Routes that support filters accept them dans the same JSON input. Par exemple, observability trace listing supports pagination et route-supported filters:

```bash
mastra api trace list '{"page":0,"perPage":20,"filters":{"spanType":"agent"}}'
```

### Obtenir command-specific help

Chaque `mastra api` leaf command includes command-specific examples dans its help output. Use `--help` sur the exact command you want à call:

```bash
mastra api agent run --help
mastra api tool execute --help
mastra api memory current update --help
mastra api workflow run resume --help
```

Use `--schema` sur commands that accept JSON input à inspect the requête shape returned par the target server:

```bash
mastra api agent run --schema
mastra api thread create --schema
mastra api score create --schema
```

Some commands ont important runtime requirements. Par exemple, `mastra api memory current update` requires working memory à be activé pour the memory instance, et `mastra api workflow run resume` only works pour suspended Workflow runs.

## Telemetry

Par défaut, Mastra collects anonymous information concernant your project like your OS, Mastra version ou Node.js version. Vous pouvez read the [source code](https://github.com/mastra-ai/mastra/blob/main/packages/cli/src/analytics/index.ts) à check what's collected.

Lorsqu’un server started avec `mastra dev` ou `mastra start` possède observability metrics enabled, Mastra also sends anonymous, aggregated modèle usage à startup: input et output token counts per provider et model, plus the command (`dev` ou `start`) et `NODE_ENV`. No prompts, responses, ou autre message content est ever sent. Vous pouvez read the [source code](https://github.com/mastra-ai/mastra/blob/main/packages/core/src/telemetry/usage-telemetry.ts) à check what's collected.

At server startup, Mastra also sends an anonymous project-surface snapshot: counts de registered agents, agent controllers, workflows, tools, processors, vector stores, scorers, workspaces, MCP servers, gateways, et channels, plus booleans pour memory, voice, editor, et observability usage et the coarse storage backend category. It doesn't envoie names ou identifiers. Vous pouvez read the [source code](https://github.com/mastra-ai/mastra/blob/main/packages/core/src/telemetry/feature-telemetry.ts) à check what's collected.

Vous pouvez opt out de tous les CLI et usage analytics par setting an environment variable:

```bash
MASTRA_TELEMETRY_DISABLED=1
```

Vous pouvez également définit this tandis que using autre `mastra` commands:

```bash
MASTRA_TELEMETRY_DISABLED=1 mastra dev
```
