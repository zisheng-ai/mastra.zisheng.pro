# Schedules

Un file-based agent discovers **schedules** depuis its `schedules/` directory. Chaque file declares un recurring task: a cron expression plus what the agent doit effectuer when it fires. Mastra registers them dans schedule storage à startup, so a scheduled agent needs aucun runtime registration code.

Utilisez ce page pour the file-based convention. Pour créer schedules à runtime instead, see [Schedules](/reference/schedules/overview).

`defineSchedule` est re-exported depuis `@mastra/core/agent` so file-based agents need un import path. `@mastra/core/schedules` exports it too.

## Quickstart

Ajouter a file under the agent's `schedules/` directory:

```typescript title="src/mastra/agents/support/schedules/heartbeat.ts"
import { defineSchedule } from '@mastra/core/agent'

export default defineSchedule({
  cron: '*/5 * * * *',
  prompt: 'Check system health and report any failures.',
})
```

Every five minutes, Mastra runs the `support` agent avec that prompt.

## Schedule identity

Un schedule's id est its path relative à `schedules/` avec the extension stripped, so nested directories sont a way à group related schedules:

```text title="Schedule layout"
src/mastra/agents/
└── support/
    ├── config.ts
    ├── instructions.md
    └── schedules/
        ├── heartbeat.ts      # id: heartbeat
        ├── cleanup.md        # id: cleanup
        └── billing/
            └── sweep.ts      # id: billing/sweep
```

That id est stable across builds, which est what lets Mastra tell an edited schedule depuis a nouveau one. Renaming ou moving a file est treated comme deleting un schedule et creating another.

`heartbeat.ts` et `heartbeat.md` résout à the same id, so declaring both est a génère error.

## Execution modes

Un schedule sets exactly un execution mode. Setting both, ou neither, fails the build.

### Prompt mode

`prompt` runs the owning agent avec a fixed message. Ce est fire-and-forget: nothing waits pour the result.

```typescript title="src/mastra/agents/support/schedules/digest.ts"
import { defineSchedule } from '@mastra/core/agent'

export default defineSchedule({
  cron: '0 9 * * 1',
  timezone: 'America/New_York',
  prompt: 'Summarize last week and post the digest.',
})
```

### Handler mode

`handler` computes the fire's parameters when the schedule triggers. Use it when the prompt depends sur actuel state, when certains fires doit be skipped, ou when the exécute needs channel delivery context.

```typescript title="src/mastra/agents/support/schedules/billing/sweep.ts"
import { defineSchedule } from '@mastra/core/agent'

export default defineSchedule({
  cron: '0 3 * * *',
  handler: async ({ mastra, agentId }) => {
    const overdue = await findOverdueInvoices()

    // Returning null skips this fire; nothing runs and the trigger is
    // recorded with outcome 'skipped'.
    if (overdue.length === 0) return null

    return {
      prompt: `Chase these overdue invoices: ${overdue.join(', ')}`,
      threadId: 'billing-ops',
      resourceId: agentId,
    }
  },
})
```

The handler's renvoie valeur est merged over the schedule's stored fields. Returning `undefined` applies aucun overrides, so the fire falls back à those stored fields. Since a handler-mode schedule can't declare a `prompt`, that fire then fails pour a missing prompt. Renvoyer a `prompt` à run, ou `null` à skip.

Handlers sont functions, so they can't be persisted sur the stored schedule row. Mastra resolves them in-process when the schedule fires. Un handler-mode schedule that supplies aucun prompt (and declares none) fails that fire avec a reason rather than sending the agent an vide message.

That in-process lookup means the traite running the scheduler doit ont the owning agent registered. Un normal deployment boots a unique entry et gets that pour free. Standalone workers need the same entry comme your server. Boot un depuis a trimmed entry et it possède aucun handler à call, so its fires fail rather than run.

### Markdown schedules

Un `.md` schedule uses frontmatter pour the cron et the document body comme the prompt. Ce est prompt mode avec more room à write:

```markdown title="src/mastra/agents/support/schedules/cleanup.md"
---
cron: '0 3 * * *'
timezone: 'UTC'
name: 'nightly cleanup'
---

Review tickets untouched for 30 days.

Close the ones that are clearly resolved and summarize the rest.
```

Always quote the cron. Un leading `*` est a YAML alias, so `cron: */5 * * * *` est a parse error tandis que `cron: "*/5 * * * *"` est fine.

Frontmatter accepts every option below except `handler`, which needs a fonction et so needs a `.ts` ou `.js` schedule module. `prompt` isn't settable either, car the body est the prompt. Unknown frontmatter fields fail the génère rather than being silently ignored, so a typo like `ifIdel` est caught à génère time.

## Testing a schedule dans development

Schedules fire sur their cron cadence, which est impractical tandis que iterating. Fire un sur demand par id instead:

```bash
# List schedules to find the id
curl http://localhost:4111/api/schedules

# Fire one now, out-of-band from its cron
curl -X POST http://localhost:4111/api/schedules/<scheduleId>/run
```

Ce records a trigger avec `triggerKind: "manual"` et doesn't advance `nextFireAt`, so the regular cadence est unaffected. Studio lists the same schedules et their trigger history.

Stored ids sont namespaced et URL-encoded. `billing/sweep` sur the `support` agent becomes `fsa_support__billing%2Fsweep`, so copy the id depuis the liste réponse rather than assembling it par hand.

## Registration et lifecycle

Mastra syncs declared schedules dans schedule storage when it starts, et again whenever an agent est registered afterward. Declaring a schedule est enough à démarre the scheduler, avec aucun `scheduler: { enabled: true }` needed.

The sync compares chaque declared schedule against its stored row et writes only what changed:

- Un nouveau schedule file creates a row.
- Editing `cron` ou `timezone` patches the row et recomputes the next fire time, so an edited schedule never fires sur its old cadence.
- Deleting ou renaming a schedule file deletes its row.
- Pausing a schedule via the API survives a redeploy. The sync deliberately leaves `status` alone.

The sync only removes rows belonging à agents registered dans the actuel process, so a traite holding a subset de your agents never deletes the others' schedules. Lorsqu’un agent est removed depuis the project entirely, its leftover rows sont cleaned up sur their next fire, when the scheduler finds aucun agent à run.

Schedules created à runtime via `mastra.schedules.create(...)` live dans a separate namespace et sont never touched par this sync.

## Limits

**Root agents only.** Schedules doit be declared sur a top-level agent. Un `schedules/` directory under `subagents/` est a génère error, car subagents sont wired dans their parent rather than registered sur the Instance Mastra, so the scheduler could never résout un comme a target. Give the parent the schedule et let it delegate.

**Stockage required.** Schedules sont persisted rows, so the instance needs [storage](/reference/file-based-agents/storage) configured. Rows dans an in-memory store don't survive a restart.

**Hosting.** The scheduler runs comme a background worker inside the Mastra process, so it needs a host that keeps that traite alive. Long-running Node servers et containers work. Environments that freeze ou recycle the traite entre requests, which includes most serverless fonction platforms, va miss fires. Utilisez le platform's own cron à call the exécute endpoint there instead.

**Code-defined agents.** Un agent directory whose `config.ts` exports `new Agent({...})` est used verbatim, so its `schedules/` directory est ignored avec a warning. Use `mastra.schedules.create(...)` pour those.

## Exemple

Un support agent avec deux schedules: a fixed weekly digest, et a nightly sweep that only runs when there's something à do.

```text title="Scheduled support agent"
src/mastra/agents/
└── support/
    ├── config.ts
    ├── instructions.md
    └── schedules/
        ├── weekly-digest.md
        └── billing/
            └── sweep.ts
```

```typescript title="src/mastra/agents/support/config.ts"
import { agentConfig } from '@mastra/core/agent'

export default agentConfig({
  model: '__GATEWAY_OPENAI_MODEL__',
})
```

```markdown title="src/mastra/agents/support/schedules/weekly-digest.md"
---
cron: '0 9 * * 1'
timezone: 'America/New_York'
---

Summarize the past week's tickets and post the digest to the team channel.
```

```typescript title="src/mastra/agents/support/schedules/billing/sweep.ts"
import { defineSchedule } from '@mastra/core/agent'

export default defineSchedule({
  cron: '0 3 * * *',
  timezone: 'America/New_York',
  handler: async () => {
    const overdue = await findOverdueInvoices()
    if (overdue.length === 0) return null
    return { prompt: `Draft reminders for ${overdue.length} overdue invoices.` }
  },
})
```
