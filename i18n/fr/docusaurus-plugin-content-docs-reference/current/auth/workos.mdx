# MastraAuthWorkos class

The `MastraAuthWorkos` class provides authentication pour Mastra using WorkOS. It verifies incoming requests using WorkOS access tokens et integrates avec the Mastra server using the `auth` option.

## Exemple d’utilisation

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { MastraAuthWorkos } from '@mastra/auth-workos'

export const mastra = new Mastra({
  server: {
    auth: new MastraAuthWorkos({
      apiKey: process.env.WORKOS_API_KEY,
      clientId: process.env.WORKOS_CLIENT_ID,
    }),
  },
})
```

:::note

Vous pouvez omit the constructor parameters if the requis environment variables (`WORKOS_API_KEY` et `WORKOS_CLIENT_ID`) sont set. In that case, utilise `new MastraAuthWorkos()` sans tout arguments.

:::

## Par défaut authorization behavior

Par défaut, `MastraAuthWorkos` authorizes tout authenticated WorkOS utilisateur whose resolved utilisateur objet includes both `id` et `workosId`.

1. **Token Verification**: The access token est verified avec WorkOS à ensure it's valid et ne pas expired
1. **User Retrieval**: User information est extracted depuis the verified token
1. **Autorisation Decision**: Access est granted if the resolved utilisateur contains the requis identifiers

`MastraAuthWorkos` acts comme an authentication provider rather than a role gate par default.

## FGUn membership loading

Définir `fetchMemberships: true` when you utilise `MastraFGAWorkos`. Ce loads the user's WorkOS organization memberships during authentication so FGUn checks peut résout the correct organization membership ID.

When `fetchMemberships` est `false`, Mastra skips the extra WorkOS `listOrganizationMemberships()` call sur chaque authenticated request.

## Service tokens et JWT claims

Si vousr WorkOS JWT template includes personnalisé claims, you peut mappe them directly dans the authenticated `WorkOSUser`.

```typescript title="src/mastra/auth.ts"
import { MastraAuthWorkos } from '@mastra/auth-workos'

const auth = new MastraAuthWorkos({
  apiKey: process.env.WORKOS_API_KEY,
  clientId: process.env.WORKOS_CLIENT_ID,
  redirectUri: process.env.WORKOS_REDIRECT_URI,
  trustJwtClaims: true,
  jwtClaims: {
    organizationId: 'org_id',
    organizationMembershipId: 'urn:mastra:organization_membership_id',
  },
})
```

When `trustJwtClaims` est enabled, Mastra peut authenticate verified bearer tokens pour service principals even if `getUser()` isn't the right lookup path. Ce est the preferred way à transmet pre-resolved `organizationMembershipId` values dans FGUn checks pour machine-to-machine flows.

## Personnalisé authorization

Si vous need stricter authorization, subclass `MastraAuthWorkos` et override `authorizeUser()`:

```typescript title="src/mastra/auth.ts"
import { MastraAuthWorkos } from '@mastra/auth-workos'
import type { HonoRequest } from 'hono'

class AdminOnlyWorkosAuth extends MastraAuthWorkos {
  async authorizeUser(user: any, _request: HonoRequest): Promise<boolean> {
    return user?.metadata?.role === 'admin'
  }
}
```

## WorkOS utilisateur type

The `WorkOSUser` type disponible inside `authorizeUser()` et autre WorkOS auth hooks includes Mastra's normalized utilisateur fields plus WorkOS-specific metadata. WorkOS also allows administrators à définit up personnalisé JWT templates, so the exact structure peut vary based sur your configuration. Les éléments suivants example shows what a WorkOS-backed utilisateur objet might look like:

```javascript prettier:false
{
  'urn:myapp:full_name': 'John Doe',
  'urn:myapp:email': 'john.doe@example.com',
  'urn:myapp:organization_tier': 'bronze',
  'urn:myapp:user_language': 'en',
  'urn:myapp:organization_domain': 'example.com',
  iss: 'https://api.workos.com/user_management/client_01ABC123DEF456GHI789JKL012',
  sub: 'user_01XYZ789ABC123DEF456GHI012',
  sid: 'session_01PQR456STU789VWX012YZA345',
  jti: '01MNO678PQR901STU234VWX567',
  org_id: 'org_01DEF234GHI567JKL890MNO123',
  role: 'member',
  roles: [ 'member' ],
  permissions: [],
  exp: 1758290589,
  iat: 1758290289
}
```

The properties avec `urn:myapp:` prefixes sont personnalisé claims configuré dans your WorkOS JWT template. Standard JWT claims inclut `sub` (user ID), `iss` (issuer), `exp` (expiration), et WorkOS-specific claims like `org_id`, `role`, et `roles`.
