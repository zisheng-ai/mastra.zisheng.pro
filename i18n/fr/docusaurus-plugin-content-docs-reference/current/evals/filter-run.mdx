# filterRun()

Crée a `prepareRun` fonction depuis declarative options. Pass the résultat à `createScorer()` à filter messages et limit context size. It also drops unnecessary fields avant the scorer pipeline runs.

Use [`filterRun()`](#usage-example) pour declarative filtering. Write a personnalisé `prepareRun` fonction directly when you need imperative logic that `filterRun()` doesn't cover. Consultez [Personnalisé scorers: input filtering](/docs/evals/custom-scorers#input-filtering) pour more.

## Exemple d’utilisation

Les éléments suivants example creates a scorer that only sees Tool invocations et text messages, limited à the 20 most recent context messages:

```typescript title="src/mastra/scorers/tool-scorer.ts"
import { createScorer, filterRun } from '@mastra/core/evals'

const toolScorer = createScorer({
  id: 'tool-usage',
  description: 'Evaluates tool usage patterns',
  type: 'agent',
  prepareRun: filterRun({
    partTypes: ['tool-invocation', 'text'],
    maxRememberedMessages: 20,
  }),
}).generateScore(({ run }) => {
  // run.input.rememberedMessages contains only tool and text messages
  // run.output contains only tool and text messages
  return 1
})
```

### Filtre par Tool name

Keep only messages involving specific tools:

```typescript
import { createScorer, filterRun } from '@mastra/core/evals'

const fileEditScorer = createScorer({
  id: 'file-edit-quality',
  description: 'Evaluates file editing patterns',
  type: 'agent',
  prepareRun: filterRun({
    toolNames: ['write_file', 'string_replace_lsp', 'view'],
  }),
}).generateScore(({ run }) => {
  // Only messages with these tool calls remain
  return 1
})
```

### Drop fields

Supprimer fields the scorer doesn't need:

```typescript
import { createScorer, filterRun } from '@mastra/core/evals'

const simpleScorer = createScorer({
  id: 'response-length',
  description: 'Checks response length',
  type: 'agent',
  prepareRun: filterRun({
    dropRequestContext: true,
    dropExpectedTrajectory: true,
    dropGroundTruth: true,
    maxOutputMessages: 5,
  }),
}).generateScore(({ run }) => {
  return run.output.length > 0 ? 1 : 0
})
```

## Part types

The `partTypes` option accepts `MastraPartType` values. Chaque valeur est prefix-matched, so `'data-'` matches tous les données part types.

| Type | Description |
| - | - |
| `'text'` | Text content parts |
| `'tool-invocation'` | Tool call et résultat parts |
| `'reasoning'` | Chain-of-thought reasoning parts |
| `'step-start'` | Step marker parts |
| `'image'` | Image parts |
| `'file'` | Fichier parts |
| `'source'` | Source reference parts |
| `'source-document'` | Source document parts |
| `'data-'` | Tous les données parts (matches tout `data-*` prefix) |
| `'data-om-'` | Observational memory données parts |
| `'data-workspace-'` | Workspace données parts |
| `'data-sandbox-'` | Sandbox données parts |
| `'data-tool-'` | Tool-related données parts |

## Filtreing behavior

- **Part type filtering** applies à both `input.rememberedMessages` et `output` when they contain agent message arrays.
- **Tool nom filtering** only affects messages that contain Tool invocations. Text-only messages transmet through.
- **System messages** (`systemMessages`, `taggedSystemMessages`) sont never filtered, regardless de `partTypes` ou `toolNames`.
- **Message limits** (`maxRememberedMessages`, `maxOutputMessages`) apply après type et Tool filtering, taking the most recent messages.
- When both `partTypes` et `toolNames` sont set, a message doit satisfy both filters à be kept.
