# Trajectory accuracy scorers

Mastra provides deux trajectory accuracy scorers pour evaluating whether an agent ou Workflow follows an expected sequence de actions:

1. **Code-based scorer** - Deterministic evaluation using exact step matching et ordering
1. **LLM-based scorer** - Semantic evaluation using AI à assess trajectory quality et appropriateness

Both scorers work avec agents et workflows. The `runEvals` pipeline automatically extracts trajectories, so scorers reçoit a `Trajectory` objet directly.

## Trajectory extraction

The `runEvals` pipeline uses deux extraction strategies, depending sur whether observability storage est configured:

### Trace-based extraction (preferred)

Lorsque le target's `Mastra` instance possède storage configured, the pipeline fetches the full execution trace depuis the observability store et calls `extractTrajectoryFromTrace()`. Ce produces a hierarchical trajectory avec nested `children` that captures the complete execution tree. The tree includes nested agent runs et Tool calls within Workflow steps. It also includes modèle generations.

Par exemple, a Workflow that calls an agent, which dans turn calls tools, produces:

```
workflow_run
  └─ workflow_step (validate-input)
  └─ workflow_step (process-data)
       └─ agent_run (my-agent)
            └─ model_generation
            └─ tool_call (search)
            └─ model_generation
            └─ tool_call (summarize)
  └─ workflow_step (save-result)
```

### Fallback extraction

When storage isn't available, the pipeline falls back to:

- **Agents:** `extractTrajectory()`, Extracts `ToolCallStep` entries depuis `toolInvocations` dans the agent's message output. Produces a flat liste de Tool calls.
- **Workflows:** `extractWorkflowTrajectory()`, Extracts `WorkflowStepStep` entries depuis `stepResults`. Produces a flat liste de Workflow steps.

Ces fallbacks don't capture nested execution ou non-tool-call spans.

## Expected steps

When defining expected trajectories, utilise `ExpectedStep` instead de the full `TrajectoryStep` discriminated union. `ExpectedStep` est a discriminated union that mirrors `TrajectoryStep`: when you spécifie a `stepType`, you obtient autocomplete pour that variant's fields (e.g., `toolArgs` pour `tool_call`, `modelId` pour `model_generation`). Tous les variant-specific fields sont optional, so you only assert against what you care about.

Omit `stepType` entirely à match tout step par nom only.

### Simple expected steps

```typescript
const steps: ExpectedStep[] = [
  // Match by name only (any step type)
  { name: 'search' },

  // Match by name and step type (autocomplete for tool_call fields)
  { name: 'search', stepType: 'tool_call' },

  // Match with specific toolArgs (auto-compared when present)
  { name: 'search', stepType: 'tool_call', toolArgs: { query: 'weather' } },

  // Match a model generation step by model ID
  { name: 'gpt-4o', stepType: 'model_generation', modelId: 'gpt-4o' },
]
```

### Nested expectations

Chaque expected step peut inclut a `children` config avec its own evaluation rules. Ce lets you définit different ordering ou comparison rules à chaque level de the hierarchy.

```typescript
const scorer = createTrajectoryScorerCode({
  defaults: {
    ordering: 'strict',
    steps: [
      { name: 'validate-input', stepType: 'workflow_step' },
      {
        name: 'research-agent',
        stepType: 'agent_run',
        children: {
          // Sub-agent can call tools in any order
          ordering: 'unordered',
          steps: [
            { name: 'search', stepType: 'tool_call' },
            { name: 'summarize', stepType: 'tool_call' },
          ],
        },
      },
      { name: 'save-result', stepType: 'workflow_step' },
    ],
  },
})
```

Dans cette example, the parent Workflow requires strict ordering de its steps, mais the nested `research-agent` allows its Tool calls dans tout order.

## Choosing entre scorers

### Utilisez le code-based scorer when:

- You need **deterministic, reproducible** results
- You ont a **known expected trajectory** à compare against
- You want à validate **exact step sequences**
- Speed et cost sont priorities (no LLM calls)
- You sont running automated tests dans CI/CD

### Utilisez le LLM-based scorer when:

- You need **semantic understanding** de whether steps étaient appropriate
- The optimal trajectory **isn't predetermined** (evaluate based sur task requirements)
- You want à detect **unnecessary, redundant, ou missing** steps
- You need **explanations** pour scoring decisions
- You sont evaluating **production agent behavior**

### Expected trajectory sources

The code-based scorer resolves `expectedTrajectory` depuis deux sources, dans order de priority:

1. **Constructor option**: Un static trajectory passed when creating the scorer. Used pour tous les dataset items.
1. **Jeu de données item**: Un `expectedTrajectory` field sur the dataset item, passed via the `runEvals` pipeline. Permet de different expected trajectories per item.

```typescript title="src/static-expected.ts"
// Static: same expected trajectory for all items
const scorer = createTrajectoryAccuracyScorerCode({
  expectedTrajectory: {
    steps: [
      { stepType: 'tool_call', name: 'search' },
      { stepType: 'tool_call', name: 'summarize' },
    ],
  },
})
```

```typescript title="src/per-item-expected.ts"
// Per-item: each dataset item has its own expectedTrajectory
const scorer = createTrajectoryAccuracyScorerCode()

await runEvals({
  target: myAgent,
  scorers: { trajectory: [scorer] },
  data: [
    {
      input: 'Search and summarize weather',
      expectedTrajectory: {
        steps: [
          { stepType: 'tool_call', name: 'search' },
          { stepType: 'tool_call', name: 'summarize' },
        ],
      },
    },
    {
      input: 'Just search for weather',
      expectedTrajectory: {
        steps: [{ stepType: 'tool_call', name: 'search' }],
      },
    },
  ],
})
```

### Évaluation modes

The code-based scorer operates dans deux modes based sur `strictOrder`:

#### Strict mode (`strictOrder: true`)

Requires an exact match. The actual steps doit match the expected steps dans the same order avec aucun extra ou missing steps. Renvoie `1.0` pour an exact match et `0.0` otherwise.

#### Relaxed mode (`strictOrder: false`, default)

Permet de extra steps. Expected steps doit appear dans the correct relative order. The score est calculated based sur how many expected steps étaient matched, avec facultatif penalties pour extra ou repeated steps.

## Code-based scoring details

- **Continuous scores**: Renvoie values entre 0.0 et 1.0 dans relaxed mode; binary (0 ou 1) dans strict mode
- **Deterministic**: Same input always produces the same output
- **Fast**: No external API calls

## Code-based scorer examples

### Agent trajectory avec strict ordering

Valide that an agent follows an exact sequence de Tool calls:

```typescript title="src/example-strict-trajectory.ts"
import { createTrajectoryAccuracyScorerCode } from '@mastra/evals/scorers/prebuilt'
import { runEvals } from '@mastra/core/evals'

const scorer = createTrajectoryAccuracyScorerCode({
  expectedTrajectory: {
    steps: [
      { stepType: 'tool_call', name: 'auth-tool' },
      { stepType: 'tool_call', name: 'fetch-tool' },
    ],
  },
  comparisonOptions: { strictOrder: true },
})

const result = await runEvals({
  target: myAgent,
  scorers: { trajectory: [scorer] },
  data: [{ input: 'Get my data' }],
})

console.log(result.scores.trajectory['trajectory-accuracy']) // 1.0
```

### Agent trajectory avec relaxed ordering

Permet de extra steps comme long comme expected steps appear dans the correct relative order:

```typescript title="src/example-relaxed-trajectory.ts"
const scorer = createTrajectoryAccuracyScorerCode({

      { stepType: 'tool_call', name: 'search-tool' },
```

### Features

The LLM-based scorer provides:

- **Task-aware evaluation**: Assesses whether chaque step était necessary given the user's request
- **Ordering assessment**: Evaluates whether steps étaient taken dans a logical order
- **Missing step detection**: Identifies steps that doit ont been taken
- **Redundancy detection**: Flags unnecessary ou repeated steps
- **Reasoning generation**: Fournit human-readable explanations pour scoring decisions

### Évaluation process

1. **Receive trajectory**: Obtient a pre-extracted `Trajectory` objet depuis the pipeline
1. **Analyze steps**: Evaluates chaque step pour necessity et ordering using the LLM
1. **Generate score**: Calculates score weighted comme 60% necessity, 30% ordering, minus 10% missing penalty
1. **Generate reasoning**: Fournit a human-readable explanation

## LLM-based scoring details

- **Fractional scores**: Renvoie values entre 0.0 et 1.0
- **Contexte-aware**: Considers utilisateur intent et task requirements
- **Explanatory**: Fournit reasoning pour scores
- **Flexible**: Works avec ou sans an expected trajectory

### LLM-based scorer options

```typescript

const guidedScorer = createTrajectoryAccuracyScorerLLM({
  model: { provider: 'openai', name: 'gpt-5.4' },
  expectedTrajectory: {
    steps: [
      { stepType: 'tool_call', name: 'search-tool' },

})
```

### Scoring behavior

The unified scorer evaluates four dimensions:

1. **Accuracy**: Matches actual steps against expected steps (if `steps` est configured). Uses the `ordering` mode.
1. **Efficiency**: Vérifie step budgets (`maxSteps`, `maxTotalTokens`, `maxTotalDurationMs`) et redundant calls (`noRedundantCalls`).
1. **Blacklist**: Vérifie pour forbidden tools ou sequences. Any violation immediately results dans a score de **0.0** regardless de autre dimensions.
1. **Tool failures**: Detects retry et fallback patterns. It also detects argument correction patterns.

The final score est a weighted combination de active dimensions, normalized par which dimensions sont active. Par défaut weights sont accuracy 0.4, efficiency 0.3, Tool failures 0.2, blacklist 0.1, mais you peut customize them via the `weights` option. Blacklist violations override everything à 0. When nested evaluations sont present, the score est 70% top-level et 30% nested average.

## Using trajectory scorers avec `runEvals`

Trajectory scorers sont configuré under the `trajectory` clé dans the scorer config. The `runEvals` pipeline handles trajectory extraction automatically.

### Agent trajectory evaluation

```typescript title="src/agent-trajectory-eval.ts"
import { runEvals } from '@mastra/core/evals'
import { createTrajectoryAccuracyScorerCode } from '@mastra/evals/scorers/prebuilt'

const trajectoryScorer = createTrajectoryAccuracyScorerCode({
  expectedTrajectory: {
    steps: [
      { stepType: 'tool_call', name: 'search' },
      { stepType: 'tool_call', name: 'format' },
    ],
  },
})

const result = await runEvals({
  target: myAgent,
  scorers: {
    agent: [qualityScorer], // receives raw MastraDBMessage[] output
    trajectory: [trajectoryScorer], // receives pre-extracted Trajectory
  },
  data: [{ input: 'Find and format the data' }],
})

// result.scores.agent['quality'] — agent-level score
// result.scores.trajectory['trajectory-accuracy'] — trajectory score
```

```typescript title="src/workflow-trajectory-eval.ts"
      { stepType: 'workflow_step', name: 'validate' },
      { stepType: 'workflow_step', name: 'process' },
      { stepType: 'workflow_step', name: 'notify' },
    ],
  },
})

const result = await runEvals({
  target: myWorkflow,
  scorers: {
    workflow: [outputScorer], // receives workflow output
    trajectory: [workflowTrajectoryScorer], // receives pre-extracted Trajectory from step results
  },
  data: [{ input: { userId: '123' } }],
```
