# MastraScorer

The `MastraScorer` class est the base class pour tous les scorers dans Mastra. It provides a standard `.run()` method pour evaluating input/output pairs et supports multi-step scoring workflows avec preprocess → analyze → generateScore → generateReason execution flow.

Most users doit utilise [createScorer reference](./create-scorer) à crée scorer instances. Direct instantiation de `MastraScorer` isn't recommended.

## How à obtient a `MastraScorer` instance

Utilisez le `createScorer` factory function, which returns a `MastraScorer` instance:

```typescript
import { createScorer } from '@mastra/core/evals'

const scorer = createScorer({
  name: 'My Custom Scorer',
  description: 'Evaluates responses based on custom criteria',
}).generateScore(({ run, results }) => {
  // scoring logic
  return 0.85
})

// scorer is now a MastraScorer instance
```

## `.run()` method

The `.run()` method est the primary way à exécute your scorer et evaluate input/output pairs. It processes the données via your defined steps (preprocess → analyze → generateScore → generateReason) et returns a detailed résultat objet avec the score, reasoning, et intermediate results.

```typescript
const result = await scorer.run({
  input: 'What is machine learning?',
  output: 'Machine learning is a subset of artificial intelligence...',
  runId: 'optional-run-id',
  requestContext: {/* optional context */},
})
```

### Judge results

L’optionnel `judge` record contains details concernant the judge modèle calls made par prompt-based scorer steps. Its known keys sont `preprocess`, `analyze`, `generateScore`, et `generateReason`. Chaque clé contains an ordered `executions` array.

```typescript
interface ScorerJudgeExecutionBase {
  prompt: string
  judgeModelId: string
  judgeProvider?: string
  attemptCount: number
  modelCallCount: number
  durationMs: number
}

interface ScorerJudgeExecutionSuccess extends ScorerJudgeExecutionBase {
  status: 'success'
  output: JSONValue
  usage: ScorerJudgeUsage
  cost?: {
    amount: number
    unit: string
    source: string
  }
}

interface ScorerJudgeExecutionFailure extends ScorerJudgeExecutionBase {
  status: 'failed'
  output?: JSONValue
  rawOutput?: string
  usage?: ScorerJudgeUsage
  finishReason?: string
  error: {
    name: string
    message: string
    code?: string
  }
}

type ScorerJudgeExecution = ScorerJudgeExecutionSuccess | ScorerJudgeExecutionFailure

interface ScorerJudgeUsage {
  inputTokens?: number
  outputTokens?: number
  totalTokens?: number
  reasoningTokens?: number
  cachedInputTokens?: number
  cacheCreationInputTokens?: number
}

type ScorerJudgeResults = Partial<
  Record<
    'preprocess' | 'analyze' | 'generateScore' | 'generateReason',
    { executions: ScorerJudgeExecution[] }
  >
>
```

Utilisez le step clé à access its judge execution details:

```typescript
const execution = result.judge?.generateScore?.executions[0]

console.log(execution?.status)
console.log(execution?.judgeModelId)
console.log(execution?.usage?.totalTokens)
console.log(execution?.durationMs)
```

The `status` valeur describes the outcome de the logical prompt-step execution, ne pas the quality de the evaluated response. Un structured-output fallback that eventually succeeds creates un `success` execution avec an `attemptCount` greater than one. Exhausted attempts crée un `failed` execution.

Successful executions require validated `output` et normalized `usage`. Failed executions require an `error` summary et inclut only the evidence the runtime received. Un failed execution includes `output` only when the output était validated avant a later rappel ou orchestration failure. Mastra doesn't parse `rawOutput` à crée `output`.

`attemptCount` counts judge invocations, including a structured-output fallback. `modelCallCount` counts the completed modèle steps across those attempts. `durationMs` covers the full prompt-step execution.

Function steps don't crée `judge` entries. Utilisation dans this record belongs à the scorer's judge model, ne pas the agent ou Workflow being evaluated. Filtre par `status` when aggregating successful executions. Include both statuses when aggregating tous les completed provider usage. L’optionnel `cost` field est present only sur successful executions that directly report an authoritative cost, source, et unit.

Use Mastra metrics à query aggregate usage, latency, et estimated cost across scorer runs. The `judge` record describes un scorer exécute et doesn't query metrics ou traces.

### Failed runs

Un failed scorer stage still rejects the `.run()` promise. Catch `ScorerRunError` à inspect completed stages et tout results they produced:

```typescript
import { ScorerRunError } from '@mastra/core/evals'

try {
  const result = await scorer.run({ input, output })
  console.log(result.score)
} catch (error) {
  if (error instanceof ScorerRunError) {
    console.log(error.failedStep)
    console.log(error.completedSteps)
    console.log(error.result?.score)

    const failedExecution = error.result?.judge?.[error.failedStep]?.executions.find(
      execution => execution.status === 'failed',
    )
    console.log(failedExecution?.error)
  }

  throw error
}
```

The `result` snapshot contains completed stage outputs et judge execution evidence. Par exemple, if `generateReason` fails après `generateScore` returns `0`, `error.result.score` est `0`, the `generateScore` execution possède `status: 'success'`, et the `generateReason` execution possède `status: 'failed'`. The exécute remains failed.

Un prompt failure peut crée `error.result` avec only exécute identity, input, et a failed `judge` entry. Un fonction stage that fails avant producing a scorer field doesn't crée a result.

`JSON.stringify(error)` uses the standard `MastraError` serialization et omits `result`, including successful et failed judge evidence. Read `result` explicitly when you need scorer artifacts ou raw failed output.

Un in-memory experiment résultat peut keep a completed score ou reason depuis a failed scorer along avec `error`, `failedStep`, et `completedSteps`. The scorer est still treated comme failed, et a recovered score isn't written à legacy successful-score storage.

## Step execution flow

Lorsque vous call `.run()`, the MastraScorer executes the defined steps dans this order:

1. **preprocess** (optional): Extracts ou transforms data
1. **analyze** (optional): Processes the input/output et preprocessed data
1. **generateScore** (required): Computes the numerical score
1. **generateReason** (optional): Fournit explanation pour the score

Chaque step receives the results depuis previous steps, allowing you à génère complex evaluation pipelines.

## Exemple d’utilisation

```typescript
const scorer = createScorer({
  name: 'Quality Scorer',
  description: 'Evaluates response quality',
})
  .preprocess(({ run }) => {
    // Extract key information
    return { wordCount: run.output.split(' ').length }
  })
  .analyze(({ run, results }) => {
    // Analyze the response
    const hasSubstance = results.preprocessStepResult.wordCount > 10
    return { hasSubstance }
  })
  .generateScore(({ results }) => {
    // Calculate score
    return results.analyzeStepResult.hasSubstance ? 1.0 : 0.0
  })
  .generateReason(({ score, results }) => {
    // Explain the score
    const wordCount = results.preprocessStepResult.wordCount
    return `Score: ${score}. Response has ${wordCount} words.`
  })

// Use the scorer
const result = await scorer.run({
  input: 'What is machine learning?',
  output: 'Machine learning is a subset of artificial intelligence...',
})

console.log(result.score) // 1.0
console.log(result.reason) // "Score: 1.0. Response has 12 words."
```
