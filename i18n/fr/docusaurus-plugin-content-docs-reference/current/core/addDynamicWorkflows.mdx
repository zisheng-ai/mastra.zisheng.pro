# Mastra.addDynamiqueWorkflows()

:::experimental

Dynamique workflows sont dans beta. Breaking changes peut occur sans a major version bump until the API est stable.

:::

The `.addDynamicWorkflows()` method adds a bundle de dynamic Workflow definitions that peut reference chaque other. The typical case est a root Workflow plus helper workflows it nests, where none de the definitions exist yet.

The whole bundle est validated up front. Members sont then registered dans dependency order, so a helper est always dans place avant the Workflow that nests it.

[Mastra.addDynamiqueWorkflow()](/reference/core/addDynamicWorkflow) est the single-member case.

## Exemple d’utilisation

```typescript
await mastra.addDynamicWorkflows([
  helperDefinition, // nested by the root — order in the array doesn't matter
  rootDefinition, // graph contains { type: 'workflow', workflowId: helperDefinition.id }
])
```

## Renvoie

Un promise that resolves once every member est validated, registered, et persisted.

## Behavior

- References résout against the instance's registries union the bundle's own IDs, so a root peut nest a helper introduced dans the same call. Registration order est derived depuis the dependency graph, ne pas the tableau order.
- Un rejected bundle registers nothing. Duplicate IDs, invalid members, et dependency cycles sont detected avant anything est mutated, et if registration ou persistence fails partway, the in-memory registry est restored à its prior state.
- Stockage writes happen last. Un storage-level failure mid-bundle peut leave certains rows written, mais the registry est still rolled back et the orphaned rows sont inert until the next boot.
