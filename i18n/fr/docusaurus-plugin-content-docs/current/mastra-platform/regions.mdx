# Régions

Une région contrôle l’emplacement d’exécution d’un environnement de plateforme, de sa [base de données hébergée](/docs/mastra-platform/database) et de ses données d’observabilité. La région est fixée à la création de l’environnement et ne peut pas être modifiée ultérieurement.

La plateforme Mastra propose aujourd’hui deux zones de résidence, `us` et `eu`, reposant sur des régions de calcul Railway spécifiques. Les bases de données et l’observabilité suivent automatiquement la région de l’environnement.

## Choisir une région {/* #choose-a-region */}

Transmettez `--region` lors de la création ou du premier déploiement dans un environnement :

```bash
mastra deploy --env production --region eu
mastra env create staging --region us
```

`mastra deploy --region` et `mastra env create --region` acceptent tous deux la forme courte `us` / `eu` ou un code de région Railway canonique du tableau ci-dessous. La forme courte est recommandée.

Lorsqu’aucune région n’est fournie, la valeur par défaut est `us`, qui correspond à `pdx` (Portland, Oregon).

## Régions disponibles {/* #available-regions */}

Le sélecteur de résidence propose quatre régions Railway réparties sur deux zones. Les formes courtes `us` et `eu` correspondent à la valeur par défaut soulignée de chaque zone.

| Zone | Code Railway | Emplacement |
| - | - | - |
| `us` | `pdx` (par défaut) | Portland, Oregon |
| `us` | `iad` | Ashburn, Virginie |
| `us` | `sfo` | San Francisco, Californie |
| `eu` | `ams` (par défaut) | Amsterdam, Pays-Bas |

Transmettez directement un code Railway lorsque vous devez fixer un environnement à un centre de données spécifique. `us` sélectionne `pdx` et `eu` sélectionne `ams`.

:::note
D’autres régions Railway existent dans le pipeline de déploiement (par exemple Singapour, `sin`), mais ne sont pas encore proposées dans le sélecteur de résidence, car les bases de données hébergées et l’observabilité n’ont pas de placement local hors des États-Unis et de l’UE. Une région non reconnue revient à la valeur par défaut des États-Unis au lieu de s’y fixer.
:::

## Emplacement de la base de données hébergée {/* #hosted-database-placement */}

Lorsque vous attachez une [base de données limitée à un environnement](/docs/mastra-platform/database), la plateforme choisit la région du Provider la plus proche de l’environnement. Le serveur fait autorité : un `--region` explicite sur `mastra env db create <env>` est ignoré. La région de l’environnement est la source de vérité.

| Région d’environnement | Région Turso | Région Postgres (Neon) |
| - | - | - |
| `pdx` | `sjc` (San Jose) | `aws-us-west-2` (Oregon) |
| `iad` | `iad` (Ashburn) | `aws-us-east-1` (N. Virginia) |
| `sfo` | `sjc` (San Jose) | `aws-us-west-2` (Oregon) |
| `ams` | `ams` (Amsterdam) | `aws-eu-central-1` (Frankfurt) |

Les bases de données limitées au projet (partagées entre environnements) acceptent un `--region` explicite, car elles ne sont pas liées à un seul environnement. Utilisez un ID de région du Provider pour ce flag, et non la forme courte `us` / `eu` :

```bash
mastra env db create --kind turso --region fra
mastra env db create --kind neon --region aws-us-east-1
```

Turso propose plus de 20 régions et Postgres (Neon) est disponible dans les régions AWS et Azure des États-Unis, de l’UE et d’APAC. Consultez la [liste des régions Turso](https://docs.turso.tech/features/data-edge#locations) et la [liste des régions Neon](https://neon.com/docs/introduction/regions) pour la liste complète. Un code non proposé par le Provider échoue lors de l’attachement avec l’erreur du Provider.

## Colocalisation de l’observabilité {/* #observability-co-location */}

L’ingestion d’observabilité s’exécute aujourd’hui dans deux régions : **US** (Iowa, `us-central1`) et **EU** (Amsterdam). Les Traces, logs et métriques de chaque environnement sont acheminés vers la région d’ingestion correspondant à sa zone de résidence :

| Région d’environnement | Région d’observabilité |
| - | - |
| `pdx`, `iad`, `sfo`, `us` shorthand | US (Iowa) |
| `ams`, `eu` shorthand | EU (Amsterdam) |

Le calcul et les bases de données peuvent être placés dans davantage de régions Railway et Provider que ne le prend en charge l’observabilité ; la colocalisation n’est donc pas parfaite pour chaque combinaison. Un environnement de zone `us` envoie toujours sa télémétrie vers l’ingestion US, et un environnement de zone `eu` vers l’ingestion EU, même si la région Railway sous-jacente est une ville non directement desservie par un point d’ingestion. La résidence des données est préservée au niveau de la zone. La télémétrie d’un environnement `eu` ne traverse jamais vers les États-Unis.
