# Workers

當 worker 在 API 以外的獨立進程中運行時，兩者會透過 HTTP 通訊。編排 worker 會呼叫 API 的步驟執行 endpoint，在 API 伺服器上執行 Workflow 步驟。推送模式 PubSub broker（例如採用推送模式的 Google Cloud Pub/Sub）亦可直接把事件傳送到 API 的事件 endpoint。這與由 worker 自行從 broker 拉取事件的拉取模式整合方式不同。配置身份 Provider 後，兩個 HTTP endpoint 都需要身份驗證。

## 運作方式

Worker 身份驗證與 Mastra 伺服器的其他部分共用同一套身份驗證流程。編排 worker 會隨每個 HTTP 請求傳送憑證，而伺服器配置的 `authenticateToken` Provider 會驗證憑證。

| Endpoint | 使用者 | 用途 |
| - | - | - |
| `POST /api/workflows/:workflowId/runs/:runId/steps/execute` | 透過 `HttpRemoteStrategy` 運作的編排 worker | 在 API 上執行 Workflow 步驟 |
| `POST /api/workflows/events` | 推送模式 broker（GCP Pub/Sub、SNS） | 把 Workflow 事件傳送到 API |

兩條路由均設有 `requiresAuth: true`。未配置身份 Provider 時，任何人都可公開存取。

:::warning

將 worker 部署為獨立進程時，必須在伺服器上配置身份 Provider。否則，任何呼叫者都可以存取步驟執行及事件 endpoint。

:::

## 設定 worker 身份驗證

### 在伺服器上配置身份 Provider

你可以使用任何 Mastra 身份 Provider。`SimpleAuth` 很適合用於 worker token：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { SimpleAuth } from '@mastra/core/server'

export const mastra = new Mastra({
  server: {
    auth: new SimpleAuth({
      tokens: {
        [process.env.WORKER_TOKEN!]: {
          id: 'worker',
          name: 'Orchestration Worker',
          role: 'worker',
        },
      },
    }),
  },
  // ... storage, pubsub, etc.
})
```

### 設定 worker token

在每個 worker container 上，把 `MASTRA_WORKER_AUTH_TOKEN` 設為伺服器身份 Provider 可識別的 token：

```yaml title="docker-compose.yml"
services:
  api:
    environment:
      WORKER_TOKEN: ${WORKER_TOKEN}
      # ... other env vars

  orchestration-worker:
    environment:
      MASTRA_WORKER_AUTH_TOKEN: ${WORKER_TOKEN}
      MASTRA_STEP_EXECUTION_URL: http://api:4111/api # Use HTTPS in production
      # ... other env vars
```

```bash title=".env"
WORKER_TOKEN=sk-worker-secret-token
```

這些範例在本機開發時使用 `http://`。在生產環境中，請使用 HTTPS URL，並透過 service mesh 或 ingress controller 終止 TLS。請參閱[安全建議](#security-recommendations)。

編排 worker 會讀取 `MASTRA_WORKER_AUTH_TOKEN`，並在每個步驟執行請求中以 `Bearer` token 傳送至 `Authorization` header。

## 身份驗證憑證類型

`HttpRemoteStrategy` 支援三種憑證格式。預設格式（`bearer`）適用於大部分設定。

### Bearer token

設定 `MASTRA_WORKER_AUTH_TOKEN` 後，strategy 會傳送 `Authorization: Bearer <token>`：

```bash
MASTRA_WORKER_AUTH_TOKEN=sk-worker-secret-token
```

### API 金鑰 header

以 `x-worker-api-key` 而非 `Authorization` 傳送憑證：

```typescript
import { HttpRemoteStrategy } from '@mastra/core/worker'

const strategy = new HttpRemoteStrategy({
  serverUrl: 'http://api:4111/api', // Use HTTPS in production
  auth: { type: 'api-key', key: process.env.WORKER_API_KEY! },
})
```

伺服器的身份 Provider 必須讀取 `x-worker-api-key` header，才能驗證這項憑證。

### 自訂 header

使用任何 header 名稱和值：

```typescript
import { HttpRemoteStrategy } from '@mastra/core/worker'

const strategy = new HttpRemoteStrategy({
  serverUrl: 'http://api:4111/api', // Use HTTPS in production
  auth: {
    type: 'header',
    name: 'X-Internal-Service-Key',
    value: process.env.INTERNAL_KEY!,
  },
})
```

## 推送模式 broker 身份驗證

使用推送模式 PubSub（例如 Google Cloud Pub/Sub）時，broker 會直接把事件 POST 至 `/api/workflows/events` endpoint，並附上本身的憑證。例如，Google Cloud Pub/Sub 會傳送由 Google 簽署的 OIDC token。

身份 Provider 的 `authenticateToken` callback 必須能識別 broker 傳送的憑證。請參閱你所用 broker 的說明文件，了解其身份驗證機制。

## 安全建議

- **為不同類型的 worker 使用不同 token。** 這樣便可撤銷單一 worker 的存取權，而不會影響其他 worker。
- **定期輪替 token。** 更新 `WORKER_TOKEN` 環境變數，然後重新啟動受影響的 container。
- **在生產環境中使用 TLS。** Worker 與 API 之間應透過 HTTPS 通訊，保障傳輸中的 token。這項要求適用於所有環境，包括 Kubernetes cluster 及 Docker 網絡。請使用 service mesh（例如 Istio、Linkerd）或終止 TLS 的 ingress，加密內部流量。
- **限制網絡存取。** 步驟執行及事件 endpoint 均屬內部用途。如情況許可，請使用網絡政策或防火牆規則，避免在公眾互聯網公開這些 endpoint。
